# 菲比啾比后端开发规范与学习路线

> 本文档专门面向当前 `feibijiubi` 后端项目。  
> 目标不是照搬 Teriteri，而是在参考它业务功能的基础上，做一个更规范、更适合新手学习、更容易长期维护的 mini-Bilibili 风格后端。

---

## 1. 项目定位

菲比啾比是一个面向学习和练手的 mini-Bilibili 风格后端项目。

它最终可以包含：

- 用户注册、登录、个人资料
- 视频投稿、视频列表、视频详情
- 评论、点赞、收藏、播放统计
- 搜索、热榜、弹幕、私信
- 文件上传、对象存储、缓存、异步任务

但是当前阶段不追求一次性实现所有复杂能力，而是优先建立标准后端工程能力。

本项目当前更重要的目标是：

```text
写得清楚 > 功能堆得多
结构规范 > 临时能跑
能解释明白 > 复制粘贴代码
逐步演进 > 一开始就上复杂架构
```

## 3. Teriteri 的正确参考方式

`docs/PROJECT_STRUCTURE_AND_KNOWLEDGE.md` 梳理的是 Teriteri 项目。Teriteri 可以作为参考，但不能照搬。

### 3.1 可以参考什么

Teriteri 适合作为：

- 功能地图参考
- 业务模块参考
- 数据表关系参考
- 视频网站后端知识点参考
- 后续扩展方向参考

例如它告诉我们一个 mini-Bilibili 后端大概需要：

```text
用户
视频
分类
评论
收藏
点赞
弹幕
私信
搜索
文件上传
后台审核
```

### 3.2 不建议照搬什么

不建议直接照搬：

- Java 8 + Spring Boot 2 的旧版本写法
- 一开始就引入 Redis、ES、OSS、Netty 的复杂架构
- `pojo` 混放 Entity、DTO、VO、ES 文档、消息体的结构
- 测试类里混入运维脚本的方式
- 配置文件包含真实敏感信息的做法
- Controller / Service 边界不够清晰的代码风格

### 3.3 本项目的原则

菲比啾比后端应该走这条路线：

```text
先规范基础分层
再实现核心业务
再补充工程能力
最后做复杂优化
```

不要一上来追求“像 Teriteri 一样功能完整”。对于新手来说，更好的路线是先把每一层为什么这么写搞懂。

```text
├── dto

│   └── UserRegisterDTO.java
├── entity
│   └── User.java
├── mapper
│   └── UserMapper.java
├── service
│   ├── auth
│   │   ├── CurrentUserService.java
```

Mapper XML：

```text

```

### 4.1 各层职责

| 层 | 职责 | 不应该做什么 |
|---|---|---|
| `controller` | 接收 HTTP 请求，调用 Service，返回统一响应 | 不写复杂业务逻辑，不直接操作数据库 |
| `service` | 定义业务接口 | 不关心 HTTP 注解和请求细节 |
| `service.impl` | 实现业务流程、校验业务规则、组织 Mapper 调用 | 不拼接前端响应格式 |
| `mapper` | 操作数据库 | 不写业务判断 |
| `entity` | 对应数据库表 | 不直接暴露给前端 |
| `dto` | 接收前端请求参数 | 不放数据库内部字段 |
| `vo` | 返回给前端的数据 | 不包含密码、密钥等敏感字段 |
| `converter` | Entity、DTO、VO 之间转换 | 不访问数据库 |
| `common` | 通用响应、异常处理 | 不放具体业务代码 |
| `config` | 配置属性和 Bean 配置 | 不写业务流程 |
| `utils` | 纯工具能力 | 不依赖具体业务状态 |

## 5. 核心调用链

以后开发每个功能，都尽量遵守下面这条链路。

以用户登录为例：

```text
前端请求
  ↓
UserAccountController.login()
  ↓
UserAccountService.login()
  ↓
UserAccountServiceImpl.login()
  ↓
UserMapper.selectByUsernameForLogin()
  ↓
UserMapper.xml SQL
  ↓
MySQL user 表
  ↓
JwtTokenServiceImpl 创建 token
  ↓
UserLoginVO 返回给前端
  ↓
ApiResponse<UserLoginVO>
```

### 5.1 为什么不能把逻辑都写在 Controller

Controller 是接口入口，它应该薄一点。

不推荐：

```java
@PostMapping("/login")
public ApiResponse<UserLoginVO> login(@RequestBody UserLoginDTO request) {
    // 校验参数
    // 查询数据库
    // 判断密码
    // 生成 token
    // 组装 VO
    // 返回响应
}
```

原因：

- Controller 会越来越长。
- 业务逻辑难以复用。
- 测试困难。
- 后续换接口形式时很难维护。

推荐：

```java
@PostMapping("/login")
public ApiResponse<UserLoginVO> login(@RequestBody UserLoginDTO request) {
    UserLoginVO loginResult = userAccountService.login(request);
    return ApiResponse.success("登录成功", loginResult);
}
```

Controller 只负责“接请求、调服务、返回结果”。

## 6. API 设计规范

### 6.1 统一路径前缀

建议所有业务接口都以 `/api` 开头。

当前已有：

```http
POST /api/auth/register
POST /api/auth/login
GET  /api/users/me
```

后续推荐：

```http
GET    /api/videos
GET    /api/videos/{id}
POST   /api/videos
GET    /api/comments?videoId=1
POST   /api/comments
POST   /api/videos/{id}/likes
DELETE /api/videos/{id}/likes
```

### 6.2 路径用名词，动作交给 HTTP 方法

推荐：

```http
GET    /api/videos/1
POST   /api/videos
PUT    /api/users/me
DELETE /api/comments/10
```

不推荐：

```http
GET  /api/getVideo
POST /api/addVideo
POST /api/deleteComment
```

### 6.3 登录注册可以使用动作路径

登录、注册不是典型 CRUD，可以用直观路径：

```http
POST /api/auth/register
POST /api/auth/login
```

这对初学者更清楚，也符合很多项目实践。

### 6.4 统一响应结构

当前项目已有：

```java
public class ApiResponse<T> {
    private Integer code;
    private String message;
    private T data;
}
```

统一返回：

```json
{
  "code": 200,
  "message": "登录成功",
  "data": {
    "token": "xxx",
    "user": {}
  }
}
```

失败返回：

```json
{
  "code": 400,
  "message": "用户名或密码错误",
  "data": null
}
```

好处：

- 前端处理简单。
- 后端风格统一。
- 错误信息集中管理。
- 后续接口文档更清晰。

## 7. DTO、Entity、VO 使用规范

### 7.1 Entity：数据库实体

Entity 对应数据库表。

例如 `User` 对应用户表。

Entity 可以包含：

- `id`
- `username`
- `passwordHash`
- `nickname`
- `avatarUrl`
- `status`
- `role`
- `createdAt`
- `updatedAt`

Entity 不应该直接作为接口返回值。

原因：

- 可能包含密码字段。
- 可能包含内部状态字段。
- 数据库结构变化会影响前端接口。

### 7.2 DTO：接收请求

DTO 用来接收前端传来的参数。

例如注册：

```java
public class UserRegisterDTO {
    private String username;
    private String password;
    private String confirmedPassword;
}
```

DTO 的特点：

- 只包含这个接口需要的字段。
- 不包含 `id`、`role`、`status` 等后端控制字段。
- 字段名尽量和前端 JSON 保持一致。

### 7.3 VO：返回响应

VO 用来返回给前端。

例如：

```java
public class UserVO {
    private Long id;
    private String username;
    private String nickname;
    private String avatarUrl;
}
```

VO 不应该包含：

- `passwordHash`
- JWT secret
- 内部删除标记
- 其他敏感字段

### 7.4 Converter：转换对象

例如：

```text
User Entity -> UserVO
```

应该放在 `converter` 中。

这样做的好处：

- Service 代码更干净。
- 转换逻辑可以复用。
- 后续字段变化集中修改。

## 8. 异常处理规范

当前项目已有：

```text
BusinessException
GlobalExceptionHandler
```

推荐业务错误都抛 `BusinessException`。

例如：

```java
if (user == null) {
    throw new BusinessException(400, "用户名或密码错误");
}
```

不要在 Service 中直接返回失败响应。

不推荐：

```java
return ApiResponse.fail(400, "用户名已存在");
```

推荐：

```java
throw new BusinessException(400, "用户名已存在");
```

原因：

- Service 不应该依赖响应格式。
- 失败处理集中到全局异常处理器。
- Controller 代码更统一。

### 8.1 建议错误码约定

当前可以先简单使用：

| code | 含义 |
|---:|---|
| 200 | 成功 |
| 400 | 请求参数错误或业务校验失败 |
| 401 | 未登录或 token 无效 |
| 403 | 无权限或账号状态异常 |
| 404 | 资源不存在 |
| 500 | 服务器内部错误 |

后续项目变复杂后，可以再抽象成 `ErrorCode` 枚举。

## 9. 登录认证规范

当前阶段建议继续使用轻量 JWT 方案，不急着引入 Spring Security。

### 9.1 当前登录流程

```text
用户提交 username/password
  ↓
Service 校验参数
  ↓
Mapper 查询用户
  ↓
比较密码
  ↓
检查账号状态
  ↓
生成 JWT token
  ↓
返回 token + user 信息
```

### 9.2 当前查询登录用户流程

```text
前端请求 Header 携带 Authorization
  ↓
CurrentUserService 解析 token
  ↓
拿到 userId
  ↓
UserMapper 根据 userId 查询用户
  ↓
返回 UserVO
```

### 9.3 后续必须优化的点

当前代码中密码还未加密，后续应尽快改为：

```text
注册时：明文密码 -> BCrypt 加密 -> 保存 passwordHash
登录时：明文密码 + passwordHash -> BCrypt 校验
```

不应该长期保存明文密码。

JWT 也要注意：

- `jwt.secret` 不要使用太短的字符串。
- 生产环境不要把密钥提交到 Git。
- 后续可以通过环境变量读取密钥。
- 后续可以加入登录拦截器，避免每个接口手动解析 token。

当前项目使用：

```text
src/main/resources/application.yml
```

里面包含：

- Spring 应用名
- MySQL 连接
- MyBatis 配置

推荐逐步调整为：


## 11. 数据库与 MyBatis 规范

### 11.1 数据库命名

推荐：

- 表名：小写下划线，例如 `user`、`video`、`video_stats`
- 字段名：小写下划线，例如 `password_hash`、`created_at`
- Java 字段：驼峰，例如 `passwordHash`、`createdAt`

MyBatis 当前已配置：

```yaml
mybatis:
  configuration:
    map-underscore-to-camel-case: true
```

因此：

```text
password_hash -> passwordHash
avatar_url    -> avatarUrl
created_at    -> createdAt
```

### 11.2 Mapper 职责

Mapper 只负责数据库操作。

可以写：

```java
User selectByUsernameForLogin(String username);
int countByUsername(String username);
void createUser(User user);
```

不应该在 Mapper 中写：

- 密码是否正确
- 用户能不能登录
- token 怎么生成
- 返回给前端什么 VO

这些都属于 Service 层职责。

建议先做简单评论：

### 第五阶段：点赞、收藏、统计

建议实现：

- 点赞视频
- 取消点赞
- 收藏视频
- 取消收藏
- 视频播放量
- 视频统计表

重点学习：

- 多对多关系
- 防止重复点赞
- 幂等接口
- 事务
- 统计字段一致性

### 第六阶段：文件上传

先做本地文件上传：

- 上传头像
- 上传封面
- 上传视频文件

后续再接 OSS。

重点学习：

- `MultipartFile`
- 文件大小限制
- 文件类型校验
- 文件路径和 URL 映射
- 不能信任前端传来的文件名

### 第七阶段：缓存与搜索

等 MySQL 基础功能稳定后再考虑。

不要一开始就直接上 ES，否则会把学习重点从业务分层转移到环境搭建和数据同步问题上。

### 第八阶段：实时功能

最后再考虑：

- WebSocket 弹幕
- 私信
- 在线状态
- 消息未读数

重点学习：

- 长连接
- 连接管理
- 登录校验
- 消息持久化
- 并发安全

## 14. 编码风格约定

### 14.1 命名

推荐：

```text
UserRegisterDTO
UserLoginDTO
UserVO
UserLoginVO
UserAccountService
UserAccountServiceImpl
UserMapper
UserConverter
```

不推荐：

```text
UserDto
user_vo
UserUtilService
DoUserThing
```

### 14.2 方法命名

推荐使用动词 + 业务对象：

```java
register
login
getCurrentUser
createVideo
getVideoDetail
listVideos
updateProfile
```

Mapper 方法可以更贴近 SQL：

```java
selectById
selectByUsernameForLogin
countByUsername
insertVideo
updateById
```

### 14.3 注释

新手阶段可以适当写注释，但不要每行都写。

推荐注释解释“为什么”：

```java
// 登录接口需要查询 passwordHash，但普通用户信息接口不能返回该字段。
User user = userMapper.selectByUsernameForLogin(request.getUsername());
```

不推荐注释重复代码本身：

```java
// 设置用户名
user.setUsername(username);
```

## 16. 当前项目后续优先优化清单

按优先级排序：

1. **密码加密**：注册保存 BCrypt 密码摘要，登录用 BCrypt 校验。
2. **参数校验标准化**：引入 Bean Validation，如 `@NotBlank`、`@Size`。
3. **登录拦截器**：统一解析 `Authorization`，避免每个接口手动处理。
4. **异常返回安全化**：500 错误不要直接拼接内部异常细节返回给前端。
5. **配置安全**：数据库密码和 JWT secret 改为本地配置或环境变量。
6. **接口文档同步**：每新增一个接口就更新 `docs/api.md`。
7. **单元测试**：先给 Service 层写简单测试。
8. **视频模块设计**：先做轻量版视频表和接口，不接 OSS。
9. **统一错误码**：后续抽 `ErrorCode` 枚举。
10. **事务管理**：涉及多表写入时使用 `@Transactional`。

## 18. 一句话原则

以后开发菲比啾比后端，默认遵守这几句话：

```text
Controller 只负责接口入口。
Service 负责业务规则。
Mapper 负责数据库。
Entity 不直接给前端。
DTO 只接收请求。
VO 只返回安全数据。
业务失败抛 BusinessException。
所有响应走 ApiResponse。
先把 MySQL 主链路写清楚，再考虑 Redis、ES、OSS、WebSocket。
```

这份文档就是后续开发菲比啾比后端时的基础规范。后面如果项目演进到更复杂阶段，可以继续升级，但不要在基础还没稳定时频繁推翻已有设计。
