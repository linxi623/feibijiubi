# 三、第一阶段：接入 BCrypt 密码加密

## 1. 开发目标

当前密码不能继续使用明文保存和明文比较，应改为安全的单向哈希。

需要完成：

- 注册时加密密码
- 登录时验证密码
- 修改密码时验证旧密码
- 修改密码时加密新密码
- 增加密码相关测试

## 2. 推荐实现方式

提供统一的 `PasswordEncoder` Bean：

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

注册时：

```java
String passwordHash = passwordEncoder.encode(request.getPassword());
user.setPasswordHash(passwordHash);
```

登录时：

```java
boolean matched = passwordEncoder.matches(
        request.getPassword(),
        user.getPasswordHash()
);
```

修改密码时也必须使用 `matches()`，不能再直接比较字符串。

## 3. 建议测试

- 注册后保存的密码不等于原始密码
- 同一个密码每次生成的 BCrypt 字符串可以不同
- 正确密码可以登录
- 错误密码不能登录
- 正确旧密码可以修改密码
- 错误旧密码不能修改密码
- 修改密码后旧密码不能登录
- 修改密码后新密码可以登录

## 4. 历史密码处理

如果当前开发数据库中已有明文密码，可以选择以下方案之一：

### 开发阶段推荐方案

清理测试用户，重新注册。

### 兼容迁移方案

登录时判断密码是否为 BCrypt 格式：

1. 如果已经加密，正常使用 `matches()`；
2. 如果还是旧明文，先验证明文；
3. 验证成功后立即升级为 BCrypt；
4. 后续删除兼容代码。

初学阶段建议使用第一种方案，避免长期维护不安全的兼容逻辑。

## 5. 完成标准

- [ ] 数据库不再新增明文密码
- [ ] 注册、登录、修改密码全部使用 BCrypt
- [ ] 密码相关测试通过
- [ ] 删除明文密码 TODO
- [ ] 文档不再展示真实或明文密码

# 四、第二阶段：参数校验和统一异常处理

## 1. 开发目标

将分散在 Service 中的基础格式校验逐步迁移到 DTO，并避免向前端泄露内部异常。

需要完成：

- 引入 Bean Validation
- DTO 添加校验注解
- Controller 使用 `@Valid`
- 统一处理参数校验异常
- 系统异常只返回通用信息
- 服务端记录完整异常日志

## 2. DTO 校验示例

```java
public class UserRegisterDTO {

    @NotBlank(message = "用户名不能为空")
    @Size(min = 4, max = 20, message = "用户名长度必须在4到20个字符之间")
    private String username;

    @NotBlank(message = "密码不能为空")
    @Size(min = 8, max = 64, message = "密码长度必须在8到64个字符之间")
    private String password;

    @NotBlank(message = "确认密码不能为空")
    private String confirmedPassword;
}
```

Controller：

```java
@PostMapping("/register")
public ApiResponse<Void> register(@Valid @RequestBody UserRegisterDTO request) {
    userAccountService.register(request);
    return ApiResponse.success(null);
}
```

## 3. 校验职责划分

### DTO 负责基础格式

例如：

- 是否为空
- 字符串长度
- 数值范围
- 邮箱、手机号格式
- 集合大小

### Service 负责业务规则

例如：

- 用户名是否已存在
- 两次密码是否一致
- 视频是否存在
- 用户硬币是否足够
- 视频是否处于允许操作的状态
- 当前用户是否有权限

不要把所有校验都放进 DTO，也不要把所有校验都堆在 Controller 中。

## 4. 异常处理要求

系统异常不能直接返回：

```java
"服务器内部错误" + e.getMessage()
```

推荐方式：

```java
@ExceptionHandler(Exception.class)
public ApiResponse<Void> handleException(Exception e) {
    log.error("未处理的系统异常", e);
    return ApiResponse.fail(500, "服务器内部错误");
}
```

还应分别处理：

- `BusinessException`
- DTO 参数校验异常
- 请求参数类型转换异常
- 请求体格式错误
- 未知系统异常

## 5. 完成标准

- [ ] 主要请求 DTO 已添加校验注解
- [ ] Controller 使用 `@Valid`
- [ ] 参数错误具有统一返回格式
- [ ] 系统异常不再返回内部异常信息
- [ ] 服务端会记录完整异常日志
- [ ] Service 仍然保留必要的业务规则校验

# 五、第三阶段：视频审核模块

这是下一阶段最重要的新业务功能。

## 1. 目标业务流程

```text
用户投稿视频
  ↓
视频状态变为待审核
  ↓
管理员查询待审核列表
  ↓
管理员查看视频内容
  ↓
审核通过 / 审核驳回
  ↓
通过的视频可以公开展示
驳回的视频向投稿者展示驳回原因
```

## 2. 审核状态设计

推荐定义枚举，避免在代码中散落魔法数字：

```java
public enum VideoReviewStatus {
    PENDING(0, "待审核"),
    APPROVED(1, "审核通过"),
    REJECTED(2, "审核驳回");

    private final int code;
    private final String description;
}
```

数据库可以继续使用 `TINYINT`，Java 业务代码通过枚举表达含义。

### 状态流转规则

第一版只允许：

```text
PENDING → APPROVED
PENDING → REJECTED
```

不允许：

```text
APPROVED → APPROVED
REJECTED → REJECTED
APPROVED → REJECTED
REJECTED → APPROVED
```

如果以后需要复审或重新投稿，应单独设计新的状态流转规则。

## 3. 管理员权限

当前登录拦截只能解决“是否登录”，还需要解决“是否为管理员”。

建议第一版实现：

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface AdminOnly {
}
```

管理员拦截器负责：

1. 读取当前用户身份；
2. 检查用户角色；
3. 普通用户返回 403；
4. 管理员继续访问接口。

推荐不要只信任客户端提交的角色信息。角色必须来自经过验证的 JWT，并在安全要求提高后结合数据库中的实时用户状态判断。

## 4. 推荐接口

### 查询待审核视频

```http
GET /api/admin/videos/reviews?cursor=...&size=15
```

响应建议包含：

- 视频 ID
- 标题
- 简介
- 封面地址
- 视频地址
- 投稿用户 ID
- 投稿用户昵称
- 投稿时间
- 当前审核状态

### 审核视频

```http
PUT /api/admin/videos/{vid}/review
Content-Type: application/json
```

审核通过：

```json
{
  "approved": true,
  "reason": null
}
```

审核驳回：

```json
{
  "approved": false,
  "reason": "封面与视频内容不符"
}
```

也可以将布尔值改成更明确的枚举：

```json
{
  "result": "REJECTED",
  "reason": "封面与视频内容不符"
}
```

推荐使用枚举方案，因为它的可读性和扩展性更好。

## 5. 并发审核处理

审核状态更新必须使用带旧状态条件的原子 SQL：

```sql
UPDATE video
SET status = #{newStatus}
WHERE vid = #{vid}
  AND status = 0
  AND deleted_at IS NULL;
```

业务层根据影响行数判断：

```java
int rows = videoMapper.updateReviewStatus(vid, newStatus);
if (rows != 1) {
    throw new BusinessException(409, "视频已被其他管理员审核，请刷新后重试");
}
```

这样可以避免两个管理员同时审核同一个视频时，后提交的请求覆盖前一个结果。

## 6. 审核记录表

建议新增审核记录表：

```sql
CREATE TABLE video_review_record (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    vid INT NOT NULL,
    reviewer_uid INT NOT NULL,
    old_status TINYINT NOT NULL,
    new_status TINYINT NOT NULL,
    reason VARCHAR(500),
    reviewed_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_vid (vid),
    INDEX idx_reviewer_uid (reviewer_uid)
);
```

审核记录用于回答：

- 谁审核了视频；
- 什么时间审核；
- 审核结果是什么；
- 为什么驳回；
- 是否发生过重复审核。

更新视频状态和插入审核记录应该放在同一个数据库事务中。

## 7. 推荐代码结构

```text

  VideoReviewController.java

dto/video/
  VideoReviewDTO.java

vo/video/
  PendingVideoVO.java
  VideoReviewResultVO.java

entity/
  VideoReviewRecord.java

mapper/
  VideoReviewRecordMapper.java
  VideoMapper.java

service/video/
  VideoReviewService.java

service/impl/video/
  VideoReviewServiceImpl.java

enum/
  VideoReviewStatus.java

annotation/
  AdminOnly.java

interceptor/
  AdminInterceptor.java
```

如果当前项目暂时保持按技术层横向分包，也可以遵守现有结构，不必为了一个功能立刻重构整个项目。

## 8. 视频公开查询规则

以下公开接口只能返回审核通过的视频：

- 视频详情
- 视频 Feed
- 播放量增加
- 点赞、点踩
- 投币
- 分享
- 收藏

建议将“视频存在”和“视频可以公开访问”区分开：

```java
private Video requireExistingVideo(Integer vid)
```

用于管理员和视频作者查询。

```java
private Video requirePublishedVideo(Integer vid)
```

用于普通公开视频操作。

不要让待审核或审核驳回的视频通过公开接口增加播放量或产生互动数据。

## 9. 审核模块测试

至少覆盖：

- [ ] 未登录用户不能访问审核接口
- [ ] 普通用户不能访问审核接口
- [ ] 管理员可以查询待审核视频
- [ ] 管理员可以审核通过视频
- [ ] 管理员可以驳回视频
- [ ] 驳回时原因不能为空
- [ ] 审核不存在的视频返回 404
- [ ] 已审核视频不能重复审核
- [ ] 两个管理员并发审核时只有一个成功
- [ ] 审核状态更新失败时不插入审核记录

- [ ] 驳回视频不能通过公开详情接口访问

## 10. 完成标准

# 七、第五阶段：临时上传文件自动清理

## 1. 问题背景

以下场景可能产生 COS 垃圾文件：

- 用户上传视频后没有投稿；
- 用户上传封面后关闭页面；
- 投稿过程中数据库操作失败；
- 投稿完成后临时对象删除失败；
- 网络异常导致客户端没有继续提交。

因此需要定时清理过期临时文件。

## 2. 推荐流程

```text
定时任务开始
  ↓
分页查询已过期且未提交的临时文件
  ↓
逐个删除 COS 对象
  ↓
删除成功后更新数据库状态
  ↓
单个文件失败只记录日志
  ↓
继续处理下一条记录
```

## 3. 推荐结构

```text
service/storage/
  UploadTempFileCleanupService.java

service/impl/storage/
  UploadTempFileCleanupServiceImpl.java

task/
  UploadTempFileCleanupTask.java
```

## 4. 开发注意事项

- 每次只处理固定数量，例如 100 条；
- 不要一次加载全部过期记录；
- 单个文件失败不能中断整批任务；
- 删除 COS 成功后再更新数据库状态；
- 对“COS 中已经不存在”的对象应考虑按成功处理；
- 增加成功数量、失败数量和耗时日志；
- 多实例部署时要考虑重复执行问题；
- 第一版单实例项目可以先不引入分布式锁。

## 5. 完成标准

- [ ] 可以查询过期临时文件
- [ ] 可以批量删除 COS 临时对象
- [ ] 数据库状态与删除结果一致
- [ ] 单条失败不会中断整批任务
- [ ] 定时任务有执行日志
- [ ] 清理逻辑具有单元测试

# 八、第六阶段：评论模块

审核模块和互动测试完成后，再开发评论功能。

## 1. 第一版范围

第一版只实现一级评论：

```http
POST   /api/videos/{vid}/comments
GET    /api/videos/{vid}/comments
DELETE /api/comments/{commentId}
```

暂时不要一开始就做：

- 无限层级回复；
- 评论楼中楼；
- 评论表情包；
- 评论图片；
- 评论热度算法；
- 评论实时推送。

## 2. 评论表建议字段

```text
comment_id
vid
uid
content
created_at
deleted_at
```

后续支持回复时再增加：

```text
root_id
parent_id
reply_uid
```

## 3. 业务规则

- 只有登录用户可以发表评论；
- 只能评论已审核通过的视频；
- 评论内容不能为空；
- 评论内容必须限制长度；
- 用户可以删除自己的评论；
- 管理员可以删除违规评论；
- 删除建议使用逻辑删除；
- 创建和删除评论时同步维护评论统计；
- 评论记录和统计更新必须放在同一事务中。

## 4. 完成标准

- [ ] 可以发布一级评论
- [ ] 可以分页查询评论
- [ ] 用户可以删除自己的评论
- [ ] 普通用户不能删除他人评论
- [ ] 评论统计与实际评论数量一致
- [ ] 重复删除不会重复减少统计
- [ ] 评论接口测试通过

# 十、当前不建议立即开发的内容

项目当前仍处于单体应用核心业务建设阶段，暂时不建议立即引入：

- 微服务拆分
- Spring Cloud
- Kafka 或 RabbitMQ
- Elasticsearch
- 分布式事务框架
- 复杂推荐算法
- Redis 承载所有播放请求
- WebSocket 实时弹幕
- Kubernetes

原因不是这些技术没有价值，而是当前更应该先掌握：

- 清晰的 Controller、Service、Mapper 分层；
- DTO 与 VO 的职责；
- 参数校验；
- 统一异常处理；
- 数据库事务；
- SQL 原子更新；
- 幂等设计；
- 并发一致性；
- 单元测试和集成测试；
- 权限控制；
- 日志与问题定位。

# 十一、每个功能的标准开发流程

后续每开发一个功能，都建议按照以下步骤执行。

## 第 1 步：先写需求和业务规则

明确：

- 谁可以调用；
- 请求参数是什么；
- 成功后修改哪些数据；
- 失败时返回什么；
- 是否允许重复请求；
- 是否存在并发请求；
- 是否需要事务；
- 是否涉及权限。

## 第 2 步：设计数据库

检查：

- 字段类型是否合理；
- 是否允许为空；
- 是否需要默认值；
- 是否需要唯一约束；
- 是否需要普通索引；
- 是否需要逻辑删除；
- 是否需要记录创建和更新时间。

## 第 3 步：设计接口

明确：

- HTTP 方法；
- URL；
- PathVariable；
- Query 参数；
- 请求 DTO；
- 响应 VO；
- HTTP 和业务错误码。

## 第 4 步：实现 Mapper

Mapper 只负责数据访问：

- 查询；
- 插入；
- 更新；
- 删除；
- 原子条件更新。

不要把权限判断和复杂业务规则写进 Mapper。

## 第 5 步：实现 Service

Service 负责：

- 参数之外的业务校验；
- 权限判断；
- 状态判断；
- 多个 Mapper 的业务编排；
- 事务；
- 幂等；
- 并发冲突处理。

## 第 6 步：实现 Controller

Controller 负责：

- 接收请求；
- 获取登录用户；
- 调用 Service；
- 返回统一响应。

Controller 不应该直接调用 Mapper。

## 第 7 步：编写测试

至少测试：

- 正常流程；
- 参数边界；
- 数据不存在；
- 权限不足；
- 重复请求；
- 数据库更新失败；
- 事务回滚；
- 关键并发场景。

## 第 8 步：更新文档

每完成一个功能，都同步更新：

- API 文档；
- 数据库脚本；
- 状态值说明；
- 配置示例；
- 本地运行步骤。

## 第 9 步：运行验证

推荐执行：

```bash
./mvnw test
```

需要编译检查时：

```bash
./mvnw -DskipTests compile
```

需要完整构建时：

```bash
./mvnw package
```

不能只以“Spring Boot 可以启动”作为功能完成标准。

# 十三、最终建议

当前最合理的开发路线是：

```text
BCrypt 密码加密
  ↓
参数校验和异常处理
  ↓
管理员视频审核
  ↓
补齐互动模块测试
  ↓
临时上传文件自动清理
  ↓
评论模块
  ↓
分类、搜索、弹幕
  ↓
Redis 热门榜和性能优化
```

其中，下一个正式业务功能应该是：

> **管理员视频审核模块。**

它能够补全菲比啾比当前的核心业务链路，同时继续练习：

- 角色权限；
- 状态流转；
- 数据库事务；
- SQL 原子更新；
- 并发控制；
- 操作记录；
- 单元测试；
- 接口规范。

每个阶段都应该遵循“小步完成、测试验证、文档同步”的原则。先让单体项目的核心业务正确、清晰、可维护，再逐步引入缓存、搜索、消息队列等高级技术。
