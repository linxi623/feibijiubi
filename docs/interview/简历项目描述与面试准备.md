## 二、面试可能会问的问题（按模块）

### A. 项目总览类（必问）

**A1. 介绍一下这个项目 / 你最有挑战的模块是什么？**

标准答法（30秒版）：类 B 站视频平台后端 → 最有挑战的是互动统计链路 → 一句话讲清问题
（高频写操作直接打 MySQL 扛不住）→ 一句话讲方案（Redis 计数 + MQ 异步 + 批量聚合落库）→
一句话讲难点（可靠投递 + 幂等 + 数据一致性自愈）。等面试官追问再展开。

**A2. 为什么互动计数不直接 UPDATE 数据库？**

- 播放/点赞是典型高频小写，直接 `UPDATE video_status SET play = play + 1` 会导致行锁竞争、
  磁盘 IO 放大；一个热门视频就是一个热点行。
- 方案：写路径先落 Redis（内存原子操作，天然抗高并发），异步批量聚合后一次性写库，
  把 N 次行更新合并成 1 次。读路径也优先走 Redis。
- 代价：牺牲强一致性，换最终一致性 → 引出后面所有设计。

### B. Redis 相关

**B1. Lua 脚本在你项目里解决了什么问题？为什么不用 MULTI/EXEC？**

结合你的 `video-status-increment.lua` 答：一次互动要**原子地**完成 5 件事——
当前值 hash 自增、待落库 delta hash 自增、vid 加入 dirty set、写入幂等 key（防重复请求）、
热度 zset 加分。Lua 在 Redis 单线程内一次执行，天然原子且省 N 次 RTT；
MULTI/EXEC 不能基于中间结果做条件判断（你的脚本里有 key 存在性检查、类型校验、
返回 `NEEDS_REBUILD` 哨兵这种分支逻辑），WATCH 乐观锁在高并发下会大量重试。

**B2. 缓存和数据库的一致性怎么保证？**

分两块答：
- 分类树这类低频变更数据：Cache-Aside（读时缓存未命中回源 DB 再回填，写时失效缓存）。
- 互动统计：反过来，**Redis 是主写入口**，DB 是异步聚合的落地，靠 delta hash + dirty set +
  定时 flush 保证最终一致；Redis 数据丢失时走 `VideoStatusRebuildService` 从 DB + 已消费事件表重建。
  这个"谁是 source of truth 在不同数据上是不同的"是亮点，主动讲。

**B3. 缓存击穿/穿透/雪崩了解吗？你项目里有吗？**

诚实答：分类接口重构时考虑过击穿问题（commit 记录里就写了"可能存在缓存击穿的问题"）。
说明你知道：击穿→热点 key 过期瞬间并发回源（解法：互斥锁/逻辑过期）；穿透→查不存在的数据
（解法：空值缓存/布隆过滤器）；雪崩→大批 key 同时过期（解法：过期时间加随机抖动）。
能说出"我的分类缓存目前没做互斥回源，属于已知待改进项"反而加分。

**B4. Redis 挂了系统会怎样？**

你有 `RedisOperationException` 全局处理；登录限流、互动计数会受影响。答：读路径可以降级回源 DB，
写路径（计数）设计上依赖 Redis，Redis 恢复后靠 rebuild 机制重建；同时坦承单点 Redis 是学习项目的
简化，生产应上主从+哨兵或集群。

**B5. 固定窗口限流有什么缺陷？为什么不用滑动窗口/令牌桶？**

固定窗口的临界问题：窗口边界前后各打满一次，瞬时可达 2 倍阈值。你的场景（登录失败锁定、
上传凭证防刷）对精度要求不高、实现简单原子（INCR+EXPIRE 的 Lua 原子化，还处理了
"INCR 成功但 EXPIRE 失败导致 key 永不过期"的边界）。追求平滑可换滑动窗口日志（zset）或令牌桶，
说得出取舍即可。

### C. 消息队列 / 最终一致性（你的核心，必深挖）

**C1. 为什么要引入 Outbox 表？直接在事务里发 MQ 不行吗？**

经典问题，必须答好：
- 先发 MQ 后提交事务 → 事务回滚了消息已发出（下游消费了不存在的数据）。
- 先提交事务后发 MQ → 发送失败/宕机则消息丢失。
- **本地事务 + Outbox**：业务变更和"待发送事件"写在**同一个 DB 事务**里，保证原子性；
  独立的 Relay（`VideoStatusOutboxRelay`）轮询 outbox 表投递到 RabbitMQ，配合 publisher confirm
  确认后标记完成。至少一次投递，把"丢消息"问题转化为"重复消息"问题，交给消费端幂等解决。

**C2. 多实例部署时 Relay 会不会重复投递同一条 outbox 记录？**

答你的租约机制：`VideoStatusOutboxClaimService` 用"抢占式租约"（UPDATE ... WHERE 状态可抢 +
lease 到期时间）声明所有权，只有抢到的实例投递；实例宕机后租约到期，
`recoverExpiredLease` 回收重新投递。本质是用 DB 行级原子更新实现的简易分布式锁。

**C3. 消费端幂等怎么做的？**

答 `VideoStatusConsumptionServiceImpl`：每个事件有全局 eventId，消费前先在
`video_status_consumed_event` 表 `register`（唯一约束兜底）；重复收到时 `handleDuplicate`
比对**载荷语义哈希**——同 eventId 同哈希是重投（安全忽略/续处理），同 eventId 不同哈希
说明数据被篡改或错乱（进入 repair 流程）。Redis 侧另有 processed key 防同一请求重复入账。
两层幂等：请求级（Redis）+ 事件级（DB）。

**C4. 消息消费失败怎么办？会不会死循环重试？**

答你的异常分级体系：`RetryableMessageException`（网络类瞬时错误 → requeue/延迟重试，
有 `consumer-max-retries` 上限）、`NonRetryableMessageException`（脏数据 → 直接拒绝不重回队列，
配置了 `default-requeue-rejected: false`）、`RepairRequiredMessageException`（数据错乱 →
记录到修复日志表 `VideoStatusConsumptionRepairLog`，人工/定时修复）。手动 ack 模式，
处理成功才确认。

**C5. 消息顺序性怎么保证？点赞后马上取消赞，乱序了会怎样？**

诚实+有思考地答：RabbitMQ 单队列内 FIFO，但重试会打破顺序。你的设计里 delta 是**增量**
（+1/-1），加法满足交换律，最终聚合结果与顺序无关——这是用"设计成可交换操作"绕开顺序问题，
比强行保序更优雅。对必须保序的场景（如状态机流转）可按 vid 哈希到固定队列。

**C6. 为什么选 RabbitMQ 不选 Kafka？**

学习项目诚实答：消息量级不需要 Kafka 的吞吐；RabbitMQ 的灵活路由、手动 ack、
死信机制更贴合"可靠任务分发"场景；Kafka 更适合日志流/大吞吐场景。关键是展示你知道两者定位差异。

### D. 数据库 / 事务

**D1. 批量落库具体怎么做？怎么保证不丢不重？**

答 `VideoStatusBatchFlushServiceImpl.flushOneVideo`：按 vid 从 dirty set 取脏视频 →
读取 pending delta → 一个事务内：`video_status` 做增量 UPDATE + 记录 flush batch（批次表）→
提交后用 `video-status-delta-subtract.lua` 从 Redis delta 中减去已落库部分（而不是直接清零，
避免落库期间新增的 delta 被误删）。失败有 `VideoStatusDirtyRecoveryScheduler` 兜底重试。

**D2. 事务传播、隔离级别在项目里怎么用的？**

你的消费注册用了独立事务（`@Transactional` 指定传播行为，注册事件与业务处理解耦，
避免业务回滚把幂等记录也回滚掉——这正是 REQUIRES_NEW 的典型场景）。结合
`spring-transaction-concurrency-consistency-guide.md` 里你自己总结的内容答。

**D3. 并发审核同一个视频怎么处理？**

审核接口用状态机 + 乐观锁思路：UPDATE 带上旧状态作为条件（`WHERE status = ?`），
影响行数为 0 说明已被其他管理员抢先审核 → 返回 409"请刷新后重试"。

**D4. 游标分页为什么比 LIMIT offset 好？**

Feed 用 `{createdAt}_{vid}` 复合游标：LIMIT 大 offset 要扫描并丢弃前 N 行，越翻越慢；
游标分页走索引直接定位（`WHERE (created_at, vid) < (?, ?) ORDER BY ... LIMIT n`），
性能稳定，且插入新数据时不会重复/漏读。vid 兜底是为了处理 createdAt 相同的并列。

**D5. 逻辑删除为什么不物理删除？**

`deleted_at` 软删除：保留数据可恢复可审计；关联数据（video_status、user_video）不级联删，
避免大事务；COS 文件清理放在**事务提交后**做（先保证 DB 一致，对象存储清理失败可补偿），
这个顺序值得主动讲。

### E. 认证与安全

**E1. JWT 是无状态的，你怎么实现"退出登录立即失效"？**

无状态 JWT 无法主动过期 → 引入两个有状态补丁：
① 退出：jti 写入 Redis 黑名单，TTL = token 剩余有效期（不会无限膨胀）；
② 改密：DB 的 token_version 自增，旧 token 携带的版本号校验不过全部失效（多端下线）。
拦截器统一校验。另有 `@AllowRevokedToken` 让"已拉黑 token 再调退出"幂等返回成功。

**E2. 拦截器的鉴权体系怎么设计的？**

`LoginInterceptor` 全局拦 `/api/**`（白名单：注册/登录），解析 JWT → 校验黑名单/版本 →
把 currentUserId 写入 request attribute；`@OptionalLogin` 注解标记可选登录（带 token 则校验，
不带放行）；`AdminInterceptor` 拦 `/api/admin/**` 校验 role。注解+拦截器组合，Controller 零鉴权代码。

**E3.（大概率被抓）密码为什么是明文存储？**

不要辩解，直接答：学习阶段的已知欠账，代码里留了 TODO；正确做法是 BCrypt（自带盐、慢哈希
抗彩虹表与暴力破解），改造点在 `UserAccountServiceImpl` 的注册与登录比对两处，
配合 token_version 可平滑迁移存量用户（登录成功时顺手升级哈希）。能把改造方案说清楚，坏事变好事。

**E4. 为什么用 STS 临时密钥直传，而不是文件传到后端再转存 COS？**

大文件走后端：占用应用带宽与内存、超时风险、服务器成为瓶颈。直传方案：后端只签发
限时限桶的临时凭证（还做了申请频率限流防刷），文件流量直接前端→COS；
后端用临时文件登记表（`upload_temp_file`）校验投稿时的 key 归属与时效，防止盗用他人 key。

### F. 通用八股延伸（从项目自然引出）

- HashMap/ConcurrentHashMap（Redis hash 结构类比）
- 线程池（@Scheduled 调度线程、@Async 的执行器配置）
- MySQL 索引：video_status 主键、feed 的 (created_at, vid) 索引设计、explain
- Redis 数据结构选型：为什么计数用 hash 不用 string？（一个视频 8 个计数字段，hash 省 key、
  可 HINCRBY 单字段）为什么热度榜用 zset？
- 分布式锁：Redisson 的 watchdog 续期机制（你的 `VideoStatusVidMutex` 用了 Redisson）
  vs 手写 SETNX 的缺陷（不可重入、无续期、误删他人锁）

## 三、面试叙事建议

1. **先讲问题再讲方案**：所有设计都从"如果不这么做会怎样"讲起（面试官最想听因果，不是名词）。
2. **主动暴露一个已知缺陷 + 改进方案**：比完美人设可信得多。
3. **提设计文档**：docs/ 下有 video-status-full-flow-design.md（6万字级）等推演文档，
   面试时说"每个失败场景我都在文档里推演过"，并能现场举一个（如：落库成功但 Redis 减 delta 失败
   会怎样→为什么用减法不用清零）。
4. **承认学习来源没问题**：项目参考了 teriteri 的产品形态，但后端从零自研且方案不同
   （对方分片上传→你 STS 直传；对方直接写库→你的 MQ 聚合链路）。
