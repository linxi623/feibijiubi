# 二、退出登录：Redis JWT 黑名单

## 2.1 实现目标

退出登录后：

1. 当前请求携带的 JWT 立即失效。
2. 同一用户在其他设备或其他登录中获得的 JWT 不受影响。
3. Redis 不保存完整 JWT，只保存 Token 的唯一编号 `jti`。
4. 黑名单记录只保留到 JWT 原本的过期时间。
5. 前端收到退出成功响应后，仍然要删除本地保存的 Token。

完整流程：

```text
用户登录
  ↓
生成包含唯一 jti 的 JWT
  ↓
用户调用退出接口
  ↓
从当前 JWT 读取 jti 和过期时间
  ↓
将 jti 写入 Redis 黑名单
  ↓
Redis TTL = JWT 剩余有效时间
  ↓
后续请求经过 LoginInterceptor
  ↓
发现 jti 在黑名单中
  ↓
返回 401
```

## 2.4 给 JWT 增加 `jti`

修改：

```text
src/main/java/com/feibijiubi/backend/utils/JwtUtils.java
```

### 创建 Token 时

当前 Token 包含：

- `userId`
- `username`
- `role`
- `iat`
- `exp`

还需要增加唯一 Token ID：

```java
.setId(UUID.randomUUID().toString())
```

为什么不能只使用 `userId`？

- 同一个用户可能在多个设备登录。
- 如果以 `userId` 为黑名单 Key，退出一个设备会导致所有设备一起退出。
- `jti` 对应的是某一个具体 JWT。

### 增加读取方法

建议增加：

```java
public static String getJti(String token, String secret)
```

从：

```java
Claims#getId()
```

读取。

还需要增加：

```java
public static Date getExpiration(String token, String secret)
```

从：

```java
Claims#getExpiration()
```

读取。

这两个方法都应复用现有的：

```java
parseToken(token, secret)
```

## 2.6 扩展 TokenService

修改：

```text
src/main/java/com/feibijiubi/backend/service/auth/TokenService.java
```

在已有方法之外，建议增加：

```java
String getJti(String token);

boolean isBlacklisted(String token);

void logout(String token);
```

也可以设计成 `isRevoked`、`revoke` 等名字，但整个项目要保持统一。

修改实现：

```text
src/main/java/com/feibijiubi/backend/service/impl/auth/JwtTokenServiceImpl.java
```

### `logout(token)` 应完成

1. 解析 JWT。
2. 获取 `jti`。
3. 获取 `exp`。
4. 计算 JWT 剩余有效时间。
5. 将 `jti` 写入 Redis 黑名单。

TTL 计算原则：

```text
剩余毫秒 = expiration - 当前时间
剩余秒数 = 向上取整(剩余毫秒 / 1000)
```

不要直接使用完整的 `jwt.expire-minutes` 作为 TTL，因为 Token 可能已经使用了一段时间。

例如：

```text
JWT 总有效期：120 分钟
已经使用：30 分钟
黑名单 TTL：约 90 分钟
```

## 2.7 LoginInterceptor 检查黑名单

修改：

```text
src/main/java/com/feibijiubi/backend/interceptor/LoginInterceptor.java
```

当前流程：

```text
读取 Authorization
→ 提取 Token
→ 解析 userId
→ 解析 role
→ 写入 request attribute
```

改造后：

```text
读取 Authorization
→ 提取 Token
→ 验证 JWT 并取得 jti
→ 查询 Redis 黑名单
→ 如果已注销，返回 401
→ 解析 userId
→ 解析 role
→ 写入 request attribute
```

建议已注销 Token 返回：

```java
throw new BusinessException(401, "请先登录");
```

保持现有统一提示即可。

### `@OptionalLogin` 的行为不要改变

- 没有携带 Authorization：允许访问。
- 携带了 Authorization：Token 必须合法，并且不能在黑名单中。
- 携带已退出 Token 访问可选登录接口：仍然返回 401。

### WebMvcConfig

不要把：

```text
/api/auth/logout
```

加入登录拦截器的排除路径。

退出接口必须先确认当前 Token 是有效 Token，才能将它加入黑名单。

# 三、投稿者删除自己的视频

## 3.1 实现目标

投稿者可以删除自己发布的视频：

```http
DELETE /api/videos/{vid}/delete
Authorization: Bearer <token>
```

规则：

1. 必须登录。
2. 视频必须存在且尚未删除。
3. 当前用户必须是视频作者。
4. 不限制审核状态。
5. 数据库使用逻辑删除，不物理删除 `video`。
6. 保留 `video_status` 和 `user_video`。
7. MySQL 事务提交后，再删除 COS 中的视频和封面。

---

## 3.2 为什么使用逻辑删除

`video` 表已有：

```text
deleted_at
```

现有公开查询也已经大量使用：

```sql
deleted_at IS NULL
```

因此删除视频应执行：

```sql
UPDATE video
SET deleted_at = 当前时间
...
```

不建议执行：

```sql
DELETE FROM video
```

原因：

- `video_status` 通过外键关联 `video`。
- `user_video` 通过外键关联 `video`。
- 当前外键没有配置物理删除级联。
- 逻辑删除更方便审计、排查和未来恢复。

---

## 3.3 补齐 VideoMapper 查询字段

修改：

```text
src/main/resources/com/feibijiubi/backend/mapper/VideoMapper.xml
```

当前 `selectByVid` 缺少：

```sql
cover_key,
video_key,
deleted_at
```

删除视频时需要：

- `uid`：判断当前用户是不是作者。
- `deleted_at`：判断是否已经删除。
- `video_key`：删除 COS 视频文件。
- `cover_key`：删除 COS 封面文件。

因此 `selectByVid` 至少要补齐这些字段。

---

## 3.4 增加原子逻辑删除 Mapper

修改：

```text
src/main/java/com/feibijiubi/backend/mapper/VideoMapper.java
```

建议增加：

```java
int softDeleteByOwner(
    @Param("vid") Integer vid,
    @Param("uid") Integer uid,
    @Param("deletedAt") LocalDateTime deletedAt
);
```

修改：

```text
src/main/resources/com/feibijiubi/backend/mapper/VideoMapper.xml
```

增加逻辑删除 SQL：

```xml
<update id="softDeleteByOwner">
    UPDATE video
    SET deleted_at = #{deletedAt}
    WHERE vid = #{vid}
      AND uid = #{uid}
      AND deleted_at IS NULL
</update>
```

三个条件都很重要：

### `vid = #{vid}`

指定要删除的视频。

### `uid = #{uid}`

在数据库层再次限制只能由作者删除，不能只依赖 Java 查询后的判断。

### `deleted_at IS NULL`

避免重复删除，并处理两个并发删除请求。

不要增加审核状态条件，例如不要写：

```sql
AND status = 1
```

作者应该可以删除：

- 审核中的视频。
- 审核通过的视频。
- 被打回的视频。

`status = 3` 表示违规删除审核状态，与作者逻辑删除的 `deleted_at` 不是同一个概念。

## 3.5 完成 VideoServiceImpl.deleteVideo

修改：

```text
src/main/java/com/feibijiubi/backend/service/impl/video/VideoServiceImpl.java
```

现有空方法：

```java
@Override
public void deleteVideo(Integer currentUserId, Integer vid) {
}
```

需要增加事务：

```java
@Transactional(rollbackFor = Exception.class)
```

推荐处理顺序：

```text
1. 校验 currentUserId
2. 校验 vid
3. 根据 vid 查询视频
4. 判断视频是否存在
5. 判断视频是否已经删除
6. 判断当前用户是否是作者
7. 保存 videoKey 和 coverKey
8. 执行原子逻辑删除 SQL
9. 检查受影响行数
10. 注册事务提交后的 COS 清理
```

### 建议错误语义

| 情况 | 状态码 | 提示示例 |
|---|---:|---|
| 未登录 | 401 | 请先登录 |
| vid 为空或小于等于 0 | 400 | 视频参数不合法 |
| 视频不存在 | 404 | 视频不存在 |
| 视频已经删除 | 404 | 视频不存在 |
| 当前用户不是作者 | 403 | 你无权删除此视频 |
| 条件更新影响 0 行 | 409 | 视频已被删除，请勿重复操作 |
| 数据库异常 | 500 | 视频删除失败 |

### 为什么查询后还要使用条件更新

只进行以下操作仍然存在并发问题：

```text
查询视频未删除
→ 执行普通 UPDATE
```

两个请求可能同时查询到未删除状态。

通过：

```sql
AND deleted_at IS NULL
```

保证最终只有一个请求更新成功：

```text
请求 A：影响 1 行，删除成功
请求 B：影响 0 行，返回并发冲突
```

只有影响行数为 1 时，才允许注册 COS 清理。

## 3.6 事务提交后清理 COS

数据库事务和腾讯云 COS 不属于同一个事务。

错误顺序：

```text
先删除 COS
→ 再更新数据库
```

如果 COS 删除成功，但数据库更新失败或事务回滚，就会出现：

```text
数据库显示视频仍存在
但视频文件已经丢失
```

正确顺序：

```text
数据库逻辑删除
→ MySQL 事务提交
→ 删除 COS 视频
→ 删除 COS 封面
```

可使用 Spring：

```text
TransactionSynchronizationManager
TransactionSynchronization
```

在事务中注册：

```java
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            // 删除视频文件
            // 删除封面文件
        }
    }
);
```

建议注册前确认：

```java
TransactionSynchronizationManager.isSynchronizationActive()
```

避免方法意外未运行在事务环境中。

---

## 3.7 COS 删除异常处理

`VideoServiceImpl` 已有类似方法：

```java
deleteFormalObjectQuietly(...)
deleteTempObjectQuietly(...)
```

可以复用这种“安静删除”模式，或整理成通用私有方法：

```text
key 为空 → 直接返回
调用 fileStorageService.deleteObject(key)
发生异常 → 记录 warn 日志，不继续向外抛
```

视频和封面要分别捕获异常：

```text
视频文件删除失败
→ 记录日志
→ 仍然继续删除封面
```

COS 删除失败时：

- 不恢复 `deleted_at`。
- 不回滚已提交的数据库事务。
- 不向用户返回“数据库删除失败”。
- 记录日志，后续可增加定时任务、消息队列或清理任务表进行补偿。

原因是 afterCommit 执行时，数据库已经提交，无法再真正回滚。

## 3.8 不删除关联数据

本次不删除：

```text
video_status
user_video
```

原因：

- 它们仍然通过外键关联 `video`。
- 视频记录只是被标记为删除，没有物理消失。
- 统计和用户行为数据可以用于审计与未来恢复。
- 对外查询通过 `video.deleted_at IS NULL` 隐藏视频。

后续增加评论、弹幕等表时，也需要统一考虑逻辑删除后的隐藏规则。

## 6.2 手动验证退出登录

2. 启动后端。
3. 登录得到 Token A。
4. 使用 Token A 访问受保护接口，应成功。
5. 调用退出接口。

1. 使用视频作者的 Token 调用删除接口。
2. 检查 `video.deleted_at` 已写入。
3. 检查 `video_status` 记录仍存在。
4. 检查 `user_video` 记录仍存在。

7. 检查 COS 中视频和封面对象已被清理。
8. 使用其他用户 Token 删除该视频，应返回 403。
9. 并发或重复删除时，只有第一次成功。

# 七、容易踩坑的地方

1. **退出接口只返回成功，但没有把 Token 加入黑名单。** 这种情况不是真正退出。
2. **Redis 保存完整 JWT。** 应保存 `jti`，避免敏感 Token 泄露。
3. **使用 userId 作为黑名单 Key。** 会导致同一用户所有设备一起退出。
4. **黑名单没有 TTL。** Redis 数据会持续增长。
5. **黑名单 TTL 使用完整有效期。** 应使用当前 JWT 的剩余有效时间。
6. **把 logout 加入 LoginInterceptor 排除路径。** 退出接口应要求当前有效 Token。
7. **只在 Java 中判断视频作者，SQL 更新不校验 uid。** 应同时在 SQL 层限制作者。
8. **视频删除 SQL 没有 `deleted_at IS NULL`。** 会导致重复删除和并发处理不清晰。
9. **先删 COS，再提交数据库。** 数据库回滚时会造成文件已经丢失。
10. **COS 一个文件删除失败后，不再尝试另一个文件。** 两个对象应分别处理异常。
11. **把作者删除当成审核状态 3。** 作者删除使用 `deleted_at`，状态 3 仍表示违规删除审核状态。
12. **物理删除 video。** 当前关联表和外键结构更适合逻辑删除。
