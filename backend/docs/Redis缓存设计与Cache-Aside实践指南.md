# Redis 缓存设计与 Cache Aside 实践指南

## 1. 核心结论

理论上，大多数能够序列化的数据都可以存入 Redis，并采用以下查询流程：

```text
接收查询请求
    ↓
查询 Redis
    ↓
是否命中？
 ┌──┴──┐
 是     否
 ↓      ↓
返回   查询 MySQL
           ↓
       是否存在？
        ┌──┴──┐
        是     否
        ↓      ↓
    写入 Redis  返回不存在
        ↓
       返回
```

这种缓存使用模式叫作 **Cache Aside（旁路缓存）**。

但是在实际工程中：

> Redis 可以缓存大多数数据，但不应该缓存所有数据。

更准确的设计原则是：

> 缓存高频访问、查询成本较高、具有较高命中率，并且允许短时间不一致的业务查询结果。

MySQL 和 Redis 的职责应当明确：

```text
MySQL：保存完整、可靠、持久化的数据，是业务数据的最终事实来源。
Redis：保存热点数据、临时状态、高频查询结果，以及适合使用内存数据结构的数据。
```

---

## 2. Redis 通常缓存的是业务对象，而不是单个字段

假设用户表包含以下字段：

```text
id
username
avatar
introduction
password
email
follower_count
```

一般不建议把每个字段都拆成一个独立的 Redis Key：

```text
user:1:username
user:1:avatar
user:1:introduction
user:1:follower_count
```

这样做会导致：

- 查询一次用户信息需要访问 Redis 多次；
- Key 的数量迅速增加；
- 修改用户信息时需要维护多个 Key；
- 很难保证多个字段之间的数据一致性；
- 业务代码与 Redis 存储结构耦合过深。

更常见的做法是按照一个完整的业务查询结果缓存：

```text
user:profile:1
```

其 Value 可以是一个 JSON 对象：

```json
{
  "id": 1,
  "username": "张三",
  "avatar": "https://example.com/avatar.png",
  "introduction": "这个人很神秘",
  "followerCount": 100
}
```

也可以根据业务需要使用 Redis Hash：

```text
Key：user:profile:1

username       张三
avatar         https://example.com/avatar.png
introduction   这个人很神秘
followerCount  100
```

因此，缓存设计的关注点不应该是：

> 数据库中的哪些字段可以放入 Redis？

而应该是：

> 哪些高频业务查询结果值得放入 Redis？

---

## 3. 哪些数据适合缓存

### 3.1 读取频繁的数据

例如：

- 分类列表；
- 视频详情；
- 用户公开资料；
- 首页推荐列表；
- 热门视频列表；
- 视频排行榜；
- 视频点赞数和播放量。

如果一份数据每秒会被读取很多次，但几分钟甚至几小时才变化一次，那么它通常很适合缓存。

---

### 3.2 更新频率较低的数据

例如视频分类：

```text
番剧
国创
动画
游戏
音乐
知识
科技
```

分类数据通常具有以下特点：

- 数据量较小；
- 几乎不会频繁修改；
- 用户访问首页时可能频繁查询；
- 即使短时间内读到旧数据，影响也比较小。

因此可以使用：

```text
category:list
```

作为缓存 Key，并设置较长的过期时间，例如 12～24 小时。管理员修改分类后，再主动删除对应缓存。

---

### 3.3 数据库查询成本较高的数据

一个视频详情接口可能需要查询和组装：

- 视频基本信息；
- 投稿者公开信息；
- 所属分类；
- 点赞数量；
- 收藏数量；
- 评论数量；
- 当前用户是否点赞或收藏。

如果每次请求都需要执行多条 SQL 或复杂的关联查询，可以缓存最终组装后的公共数据，例如：

```text
video:detail:10001
```

缓存的可以是 `VideoDetailVO`，而不一定是数据库中每张表的 Entity。

需要注意，带有“当前登录用户是否点赞”等个性化字段的结果不适合直接作为所有用户共享的缓存。可以将数据拆分为：

```text
公共视频详情：可以缓存
当前用户交互状态：单独查询或单独缓存
```

---

### 3.4 允许短时间不一致的数据

例如 Redis 中显示：

```text
视频播放量：10000
```

数据库中的实际播放量已经是：

```text
视频播放量：10005
```

对于播放量、点赞数、排行榜等展示型数据，短时间的差异通常可以接受。

但以下数据通常要求更强的一致性：

- 用户余额；
- 支付状态；
- 商品库存；
- 用户权限；
- 封禁状态；
- 视频审核状态；
- 订单状态。

这类数据不能随意依赖长时间缓存。关键业务操作可能仍然需要查询数据库或使用专门的一致性方案。

---

## 4. 为什么不应该缓存所有数据

### 4.1 Redis 内存成本较高

MySQL 主要使用磁盘保存大量数据，而 Redis 主要依赖内存。

假设系统有 100 万个视频，每个缓存对象序列化后占用约 5 KB：

```text
1,000,000 × 5 KB ≈ 5 GB
```

这还没有计算：

- Redis Key 本身的内存；
- Redis 对象元数据；
- 数据结构额外开销；
- 内存碎片；
- 主从复制；
- 持久化缓冲区。

实际占用通常会更高。

如果大部分视频长期无人访问，把全部视频提前写入 Redis 就会浪费大量内存。

更合理的方式是按需缓存：

```text
用户第一次访问视频
    ↓
缓存未命中
    ↓
查询数据库并写入缓存
    ↓
长期没人访问后，由 TTL 自动淘汰
```

---

### 4.2 缓存越多，一致性问题越多

假设数据库和 Redis 中的昵称都是“小明”：

```text
MySQL：小明
Redis：小明
```

用户修改昵称后，如果只更新数据库：

```text
MySQL：小红
Redis：小明
```

此时后续查询仍然可能读到旧昵称。

所以引入一份缓存，就必须同时考虑：

- 数据更新时如何处理缓存；
- 数据删除时如何处理缓存；
- Redis 操作失败怎么办；
- 多个并发请求是否可能写回旧数据；
- 缓存可以容忍多长时间的不一致。

缓存不是免费的性能优化，它会增加系统的一致性复杂度。

---

### 4.3 低频数据缓存后可能不会再次命中

例如：

- 很久以前发布且几乎无人访问的视频；
- 一次性的审核记录；
- 后台低频分页查询；
- 很少查看的历史私信；
- 高度随机的搜索条件。

如果一条数据写入缓存后，在过期之前没有第二次被访问，那么缓存流程反而增加了额外操作：

```text
查询 Redis
    ↓
缓存未命中
    ↓
查询 MySQL
    ↓
序列化对象
    ↓
写入 Redis
```

这种情况下，直接查询数据库可能更简单、更高效。

---

### 4.4 查询条件组合可能无限增长

例如视频搜索接口具有以下参数：

```text
keyword=Java&page=1&category=tech&order=hot
keyword=Java&page=2&category=tech&order=hot
keyword=Spring&page=1&category=knowledge&order=time
```

理论上可以为每一种组合生成缓存 Key：

```text
video:search:java:1:tech:hot
video:search:java:2:tech:hot
video:search:spring:1:knowledge:time
```

但这可能导致：

- Key 数量膨胀；
- 缓存命中率较低；
- Redis 内存浪费；
- 视频更新后不知道应该删除哪些搜索缓存；
- 缓存失效逻辑非常复杂。

因此通常只缓存固定的高频查询，例如：

- 热门关键词；
- 首页推荐；
- 固定排行榜；
- 热门分类第一页。

不需要缓存所有随机搜索条件。

---

### 4.5 敏感数据不应随意缓存

以下数据不应因为“查询方便”就直接放入普通业务缓存：

- 密码哈希；
- 身份证号；
- 完整手机号；
- 支付信息；
- 私密消息；
- 管理员敏感信息；
- 完整用户认证信息。

Redis 并不是绝对不能保存敏感数据，但必须额外考虑：

- 是否真的有缓存必要；
- 是否需要加密；
- 是否设置较短 TTL；
- 是否存在严格的访问隔离；
- Redis 是否暴露到公网；
- 日志是否可能打印缓存内容。

用户公开资料缓存中只应该保存接口需要的公开字段，不要直接序列化完整的 `User` Entity。

## 5. Cache Aside 的标准读取流程

下面以查询分类详情为例。

```java
public Category getCategory(String mainCategoryId, String subCategoryId) {
    String cacheKey = RedisKeyUtils.categoryDetail(
            mainCategoryId,
            subCategoryId
    );

    Category cachedCategory = redisUtils.get(
            cacheKey,
            Category.class
    );
    if (cachedCategory != null) {
        return cachedCategory;
    }

    Category category = categoryMapper.selectByCategoryId(
            mainCategoryId,
            subCategoryId
    );
    if (category == null) {
        throw new BusinessException("分类不存在");
    }

    redisUtils.set(
            cacheKey,
            category,
            Duration.ofHours(1)
    );

    return category;
}
```

核心流程只有四步：

1. 根据业务参数生成缓存 Key；
2. 查询 Redis，命中后直接返回；
3. 未命中时查询数据库；
4. 将数据库结果写入 Redis，然后返回。

Redis 查询或写入失败时，是否允许降级到数据库，需要根据项目的缓存工具和异常处理策略决定。对于普通查询缓存，一般应尽量保证 Redis 故障不会让核心查询功能完全不可用。

## 6. 数据修改时应该如何处理缓存

读取缓存相对简单，真正需要认真设计的是写操作。

推荐的基础策略是：

```text
先更新数据库，再删除缓存
```

例如修改用户公开资料：

```java
@Transactional
public void updateProfile(Long userId, UpdateUserProfileDTO dto) {
    int affectedRows = userMapper.updateProfile(userId, dto);
    if (affectedRows == 0) {
        throw new BusinessException("用户信息修改失败");
    }

    redisUtils.delete(RedisKeyUtils.userProfile(userId));
}
```

下一次查询时：

```text
Redis 中没有数据
    ↓
查询最新数据库数据
    ↓
重新写入缓存
```

### 为什么通常选择删除缓存，而不是直接更新缓存

如果同时更新数据库和 Redis：

```java
userMapper.updateProfile(userId, dto);
redisUtils.set(cacheKey, newProfile);
```

可能出现：

```text
数据库更新成功，但 Redis 更新失败
```

也可能在并发情况下发生旧数据覆盖新数据。

删除缓存通常更简单，因为数据库仍然是最终事实来源，后续请求会自动重建缓存。

需要注意：

> “先更新数据库，再删除缓存”是常见且实用的基础方案，但不是绝对强一致方案。

对于支付、库存等强一致业务，需要使用更严格的事务、消息、版本控制或专门的并发一致性设计。

## 7. 缓存空值与缓存穿透

假设有人不断请求一个不存在的视频：

```text
GET /videos/999999999
```

每一次请求都会执行：

```text
Redis 未命中
    ↓
查询 MySQL
    ↓
数据库中也不存在
```

如果不存在的结果不被缓存，大量此类请求会持续访问数据库，这种现象称为 **缓存穿透**。

一种常见处理方式是短时间缓存空值：

```java
Video video = videoMapper.selectById(videoId);
if (video == null) {
    redisUtils.setNullValue(
            cacheKey,
            Duration.ofMinutes(2)
    );
    throw new BusinessException("视频不存在");
}
```

空值缓存的 TTL 应当较短，例如：

```text
1～5 分钟
```

如果空值缓存时间过长，可能出现以下情况：

```text
第一次查询：数据不存在，写入空值缓存
随后创建数据：数据库已经存在
再次查询：仍然命中旧的空值缓存
```

所以创建数据后也应主动删除对应的空值缓存。

对于恶意请求，还应配合：

- 参数校验；
- 登录限制；
- 接口限流；
- 布隆过滤器（数据规模较大时）；
- 网关或安全层防护。

不能只依靠空值缓存解决所有穿透问题。

---

## 8. 缓存雪崩与 TTL 随机化

如果大量缓存使用完全相同的过期时间，例如都在 30 分钟后失效，就可能出现：

```text
大量 Key 同时过期
    ↓
大量请求同时查询数据库
    ↓
数据库瞬时压力过大
```

这种现象称为 **缓存雪崩**。

可以在基础 TTL 上增加少量随机时间：

```java
int randomMinutes = ThreadLocalRandom.current().nextInt(5, 11);
Duration ttl = Duration.ofMinutes(20 + randomMinutes);
```

最终 TTL 会分散在 25～30 分钟之间，降低大量 Key 同时失效的概率。

对于分类列表这种数据量很小、单个固定 Key 的缓存，不需要过度设计；TTL 随机化更适合大量同类型详情 Key。

---

## 9. 缓存击穿与热点数据

如果某个热门视频的详情缓存刚好失效，同时有大量请求访问：

```text
热点缓存失效
    ↓
大量请求同时缓存未命中
    ↓
大量请求同时查询数据库
```

这种现象称为 **缓存击穿**。

常见解决方案包括：

- 使用互斥锁，只允许一个请求重建缓存；
- 使用逻辑过期，先返回旧值，再异步更新；
- 对极热点数据设置更长 TTL；
- 对不会主动变化的数据采用更新时删除缓存的策略；
- 在流量入口进行限流和请求合并。

对于“菲比啾比”当前阶段，不建议一开始就实现复杂的逻辑过期和分布式锁。先使用普通 Cache Aside、合理 TTL 和更新时删除缓存，遇到真实热点问题后再逐步增强。

## 10. 不同业务数据的缓存策略

### 10.1 分类列表

推荐 Key：

```text
category:list
```

特点：

- 数据量小；
- 查询频率高；
- 修改频率低；
- 允许短时间不一致。

推荐策略：

```text
Cache Aside
TTL：12～24 小时
管理员修改分类后主动删除缓存
```

这是非常适合优先缓存的数据。

---

### 10.2 视频详情

推荐 Key：

```text
video:detail:{videoId}
```

特点：

- 热门视频访问频率高；
- 详情可能需要多个查询结果组合；
- 大部分公共信息允许短时间不一致；
- 视频数量可能很多，不适合全部提前缓存。

推荐策略：

```text
按需缓存
TTL：10～30 分钟，并适当增加随机值
视频修改、删除或审核状态变化后删除缓存
不存在的视频短时间缓存空值
```

---

### 10.3 用户公开资料

推荐 Key：

```text
user:profile:{userId}
```

适合缓存：

```text
用户 ID
昵称
头像
简介
公开统计信息
```

不应放入普通公开资料缓存：

```text
密码哈希
手机号
邮箱验证码
管理员敏感字段
完整认证信息
```

推荐策略：

```text
按需缓存
TTL：30～60 分钟
修改昵称、头像或简介后删除缓存
```

---

### 10.4 播放量、点赞数等计数数据

推荐 Key 示例：

```text
video:stats:{videoId}
```

可以使用 Redis Hash：

```text
playCount
likeCount
favoriteCount
commentCount
```

并使用原子增量操作：

```text
HINCRBY video:stats:1001 playCount 1
```

但这种场景已经不只是简单的查询缓存，而是让 Redis 暂时承担高频计数。

还需要考虑：

- 什么时候同步到数据库；
- Redis 故障时是否允许丢失；
- 重试是否会重复计数；
- 如何批量落库；
- 服务重启或消息重复时如何保证幂等。

因此在项目早期，可以先直接更新数据库或采用较简单的统计方案，等确实出现性能压力后再引入 Redis 聚合计数。

---

### 10.5 用户权限、封禁状态和审核状态

这类数据需要谨慎缓存。

例如管理员已经封禁用户：

```text
MySQL：已封禁
Redis：正常
```

如果鉴权逻辑仍然读取旧缓存，用户可能继续进行操作。

可选策略包括：

- 关键操作直接查询数据库；
- 设置较短 TTL；
- 状态修改后立即删除缓存；
- 使用专门的状态 Key，并在状态变化时主动更新；
- 对权限变更建立可靠的消息通知机制。

对于登录鉴权、管理员权限和封禁状态，正确性通常比减少一次数据库查询更重要。

---

### 10.6 搜索和后台分页

以下数据一般不应在项目早期进行全面缓存：

```text
任意关键词搜索
任意筛选条件组合
后台审核分页
低频管理查询
历史私信的随机分页
```

原因是：

- 参数组合过多；
- 缓存命中率可能很低；
- 数据更新后难以准确删除相关缓存；
- Key 数量和内存占用不可控。

可以只缓存经过监控确认的热门固定查询。

---

## 11. “菲比啾比”项目的 Redis 使用优先级

### 第一优先级：非常适合缓存

```text
category:list
video:hot:list
video:ranking:list
home:recommend:list
```

这些数据通常具有读取频繁、结果相对稳定的特点。

### 第二优先级：按需缓存

```text
video:detail:{videoId}
user:profile:{userId}
```

只缓存实际被访问的数据，并设置合理的过期时间。

### 第三优先级：适合 Redis 数据结构的业务数据

```text
login:token:{token}
verification:code:{email}
video:like:users:{videoId}
user:following:{userId}
```

这些数据不一定只是 MySQL 查询结果的副本，而是 Redis 的过期机制、Set、Hash 等数据结构非常适合承载对应业务。

### 暂时不建议急着缓存

```text
后台任意分页查询
审核历史记录
低频私信历史
任意组合搜索结果
用户表的全部字段
权限敏感操作结果
```

## 12. 添加缓存前的判断清单

准备为一份数据添加缓存之前，可以先回答以下问题。

### 问题一：读取是否频繁？

如果每小时只查询几次，缓存的价值可能很低。

### 问题二：数据库查询成本是否较高？

如果只是查询一张小表并且有正确索引，MySQL 本身可能已经足够快。

### 问题三：缓存命中率是否会比较高？

如果缓存写入后很少再次访问，就没有明显收益。

### 问题四：是否允许短时间读到旧数据？

如果业务要求绝对实时，就需要谨慎使用缓存。

### 问题五：修改数据时，能否明确找到需要删除的 Key？

如果一个数据变化会影响大量不可枚举的缓存 Key，维护成本会非常高。

### 问题六：缓存对象中是否包含敏感或用户个性化数据？

公共缓存不能错误地返回其他用户的私有状态。

### 问题七：Redis 不可用时，业务能否降级？

普通查询缓存通常应该允许回源数据库，而不是让 Redis 成为新的单点故障。

如果答案大致是：

```text
读取频繁：是
查询成本：较高
命中率：较高
允许短暂旧数据：是
失效范围明确：是
```

那么这份数据通常适合缓存。

如果答案大致是：

```text
读取频率：低
查询成本：低
查询组合：非常多
要求绝对实时
无法确定需要删除哪些缓存
```

那么通常不应该缓存。

## 13. 推荐的开发顺序

不要在项目一开始就给所有查询添加 Redis。更合理的演进顺序是：

### 第一阶段：先保证数据库查询正确

重点完成：

- Controller、Service、Mapper 分层；
- SQL 和索引设计；
- DTO、VO 和 Entity 职责区分；
- 参数校验；
- 异常处理；
- 接口返回结构。

### 第二阶段：识别真正的热点数据

通过接口访问频率、SQL 日志和性能测试判断：

- 哪些接口请求最多；
- 哪些 SQL 执行成本最高；
- 哪些数据重复读取最多；
- 哪些结果允许短时间不一致。

### 第三阶段：优先缓存简单且稳定的数据

例如：

```text
分类列表
排行榜
热门视频列表
```

### 第四阶段：增加详情缓存和异常场景处理

逐步加入：

- 按需缓存；
- 空值缓存；
- TTL 随机化；
- 更新数据库后删除缓存；
- Redis 故障时的查询降级。

### 第五阶段：有真实性能需求后再解决热点并发

例如：

- 缓存击穿；
- 分布式锁；
- 逻辑过期；
- 播放量批量落库；
- 消息队列异步同步。

不要为了“看起来像高并发项目”而提前引入没有真实需求的复杂度。

## 14. 总结

Redis 并不是 MySQL 的完整复制品，也不是所有查询都必须经过的固定步骤。

正确的理解是：

```text
MySQL 负责完整、持久、可靠的数据存储。
Redis 负责热点、临时、高频和适合内存结构的数据。
```

Cache Aside 的基本读取模式是：

```text
先查 Redis
    ↓
未命中时查询数据库
    ↓
把结果写入 Redis
```

而修改数据时，常见的基础策略是：

```text
先更新数据库
    ↓
再删除缓存
```

最终应当遵循以下原则：

> 不要因为一份数据“可以缓存”就缓存它，而要判断缓存它是否能够带来足够的性能收益，并且一致性、内存和维护成本是否可以接受。

对于“菲比啾比”当前阶段，建议先从分类列表、热门列表等稳定数据开始使用缓存，再根据实际访问量逐步增加视频详情和用户公开资料缓存。这样既能学习标准的 Redis 使用模式，也不会让系统过早陷入复杂的一致性问题。
