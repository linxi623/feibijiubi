# 三、Redis 到底是什么

## 3.1 最简单的理解

MySQL 主要把数据长期保存在磁盘中；Redis 主要把数据保存在内存中。

因此，Redis 的读写速度通常很快，但它不应该被简单理解成“速度更快的 MySQL”。

Redis 更适合：

- 缓存经常读取的数据；
- 保存有过期时间的临时数据；
- 原子计数；
- 分布式环境下的共享状态；
- 排行榜；
- 限流；
- 短时间去重；
- 分布式锁。

在菲比啾比中，可以把它理解成：

```text
MySQL：保存最终可信的业务数据
Redis：帮助系统快速读取、计数、限流和保存临时状态
```

## 3.2 Redis 不是 MySQL 的替代品

例如用户给视频投币时，需要修改：

- 用户硬币余额；
- 用户对视频的投币记录；
- 视频总投币数。

用户余额和投币记录属于重要业务事实，不能只保存在 Redis 中。它们仍然应该通过 MySQL 事务保证一致性。

Redis 可以帮助保存视频统计缓存，但不能因为引入 Redis 就删除原有的数据库事务。

必须记住：

> Redis 和消息队列不是数据库事务的替代品。

## 3.3 初学阶段需要掌握的数据类型

### String

适合：

- 计数；
- 限流次数；
- 临时标记；
- JWT 黑名单标记。

示例：

```text
SET login:failure:zhangsan 1 EX 600
INCR login:failure:zhangsan
```

### Hash

适合保存一个对象的多个字段。

例如视频统计：

```text
video:stats:100
  play   1000
  like   200
  coin   50
  share  30
```

常见命令：

```text
HSET video:stats:100 play 1000
HINCRBY video:stats:100 play 1
HGET video:stats:100 play
HGETALL video:stats:100
```

### Set

适合保存不重复的成员，例如某活动的参与用户集合。

初期不必强行在项目中使用。

### Sorted Set

每个成员带有一个分数，适合排行榜。

例如热门视频榜：

```text
ZINCRBY video:hot 10 video:100
ZREVRANGE video:hot 0 9 WITHSCORES
```

这个功能可以放在项目后期，不是当前最高优先级。

## 3.4 必须掌握的 Redis 命令

第一轮只需要熟悉：

```text
SET
GET
DEL
EXPIRE
TTL
INCR
DECR
HSET
HGET
HGETALL
HINCRBY
SET key value NX EX seconds
```

其中最重要的是：

```text
SET key value NX EX seconds
```

含义是：

- `NX`：只有 Key 不存在时才设置成功；
- `EX`：同时设置过期时间。

它可以用于：

- 播放去重；
- 防止短时间重复提交；
- 简单锁；
- 幂等标记。

# 四、消息队列到底是什么

## 4.1 最简单的理解

没有消息队列时，投稿接口可能同步完成很多操作：

```text
保存视频
→ 创建审核任务
→ 内容检测
→ 发送通知
→ 清理文件
→ 返回结果
```

只要其中一个外部任务很慢，用户就要一直等待。

引入消息队列后，可以改成：

```text
投稿接口保存视频
→ 向消息队列发送“视频已投稿”消息
→ 立即返回

消息消费者稍后处理：
→ 创建审核任务
→ 内容检测
→ 发送通知
→ 清理文件
```

消息队列相当于生产者和消费者之间的任务中转站。

## 4.2 三个基本角色

### Producer：生产者

负责发送消息。

在菲比啾比中，视频投稿服务可以是生产者：

```text
VideoServiceImpl.submitVideo()
  ↓
发送 VideoSubmittedEvent
```

### Broker：消息中间件

负责保存和转发消息。

本项目推荐使用 RabbitMQ。

### Consumer：消费者

负责接收并处理消息。

例如：

```text
VideoSubmittedConsumer
  ↓
接收投稿事件
  ↓
创建审核任务
```

## 4.3 为什么推荐 RabbitMQ

当前项目主要需要处理：

- 投稿后的异步审核；
- 审核后的通知；
- COS 文件清理重试；
- 一般业务事件。

RabbitMQ 的优势是：

- Spring Boot 集成相对简单；
- 本地 Docker 容易部署；
- 路由功能清晰；
- 支持确认、重试和死信队列；
- 很适合业务异步任务。

当前不建议优先学习 Kafka，因为菲比啾比暂时没有大规模日志流、埋点流或实时计算需求。

## 4.4 消息队列解决的三个主要问题

### 异步

非核心任务不阻塞主请求。

### 解耦

投稿服务只需要表达“视频已经投稿”，不需要了解通知、审核、搜索等所有后续模块。

### 削峰

大量任务同时到来时，先进入队列，消费者按照自己的处理能力逐步消费。

## 4.5 消息队列也会带来新问题

引入 MQ 后必须面对：

- 消息发送失败；
- 消息丢失；
- 消息重复；
- 消费失败；
- 消息堆积；
- 数据最终一致性；
- 消费者幂等。

因此，消息队列不是“加一个依赖、写一个监听器”就算掌握了。

# 五、开始学习前必须完成的基础

## 5.1 完善现有审核和互动功能

在引入中间件前，应先保证：

- 审核状态流转正确；
- 只有管理员可以审核；
- 只有待审核视频可以被审核；
- 点赞、取消点赞具有幂等性；
- 点踩、收藏等状态切换正确；
- 投币扣款和投币记录处于同一个事务；
- 视频统计不会因为重复请求错误增加；
- 并发请求不会轻易破坏数据。

如果业务本身还不正确，加入 Redis 和 MQ 只会让问题更难排查。

## 5.2 补充测试

至少应该有：

- 点赞与重复点赞测试；
- 取消点赞测试；
- 点赞和点踩互斥测试；
- 投币余额不足测试；
- 重复投币测试；
- 两个管理员同时审核测试；
- 已审核视频重复审核测试。

## 5.3 先理解下面几个知识

开始 Redis 前：

- MySQL 事务；
- SQL 原子更新；
- 唯一索引；
- 幂等；
- 缓存和数据库的区别。

开始 MQ 前：

- Spring 事务提交和回滚；
- 同步与异步；
- 生产者和消费者；
- 为什么消息可能重复；
- 为什么消费者必须幂等。

# 六、第 1 阶段：Redis 基础与本地环境

## 6.1 学习目标

这一阶段不要直接改核心业务，先做到：

- 能启动 Redis；
- 能使用客户端连接 Redis；
- 会执行常用命令；
- 理解 Key、Value 和 TTL；
- 能在 Spring Boot 中读写 Redis。

## 6.2 推荐环境

推荐使用 Docker Compose 管理 Redis，原因是：

- 环境可复现；
- 不污染本机；
- 以后 RabbitMQ 也可以放进同一个 Compose 文件；
- 简历项目更容易让别人启动。

如果暂时不会 Docker，也可以先在 Windows 或 WSL 中安装 Redis，但后续建议补学 Docker Compose。

## 6.3 Spring Boot 需要引入的依赖

后续开发时需要添加：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```

第一轮推荐使用 `StringRedisTemplate`，因为它的数据更直观，使用 Redis 客户端查看时也容易理解。

示例：

```java
@Service
public class RedisLearningService {

    private final StringRedisTemplate stringRedisTemplate;

    public RedisLearningService(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    public void setValue(String key, String value) {
        stringRedisTemplate.opsForValue().set(key, value);
    }
}
```

## 6.4 练习任务

先创建学习用测试，不要立即接入正式业务：

1. 写入一个字符串；
2. 读取字符串；
3. 设置 60 秒过期时间；
4. 使用 `INCR` 增加计数；
5. 使用 Hash 保存视频统计；
6. 使用 `SET NX EX` 创建临时标记；
7. 编写对应的集成测试。

## 6.5 完成标准

- [ ] 本地 Redis 可以稳定启动；
- [ ] Spring Boot 可以连接 Redis；
- [ ] 理解 Redis Key 的命名方式；
- [ ] 会使用 String 和 Hash；
- [ ] 会设置 TTL；
- [ ] 会使用 `SET NX EX`；
- [ ] Redis 不可用时能够看懂基本异常。

# 七、第 2 阶段：登录失败限制与接口限流

## 7.1 为什么把它作为第一个 Redis 业务

这个场景：

- 业务逻辑容易理解；
- 不会直接改变重要业务数据；
- 可以练习计数、TTL 和原子操作；
- 出错后的影响比互动统计小；
- 有实际安全价值。

## 7.2 登录失败限制设计

Key：

```text
login:failure:{username}
```

流程：

```text
用户登录
  ↓
查询失败次数
  ↓
是否达到上限？
  ├── 是：拒绝登录并提示稍后重试
  └── 否：继续校验密码
          ├── 密码错误：失败次数 +1，并设置 TTL
          └── 登录成功：删除失败次数
```

可以先定义：

- 10 分钟内最多失败 5 次；
- 登录成功后删除失败记录；
- 计数 Key 自动过期。

## 7.3 接口限流设计

可以先给获取 COS 上传凭证接口限流：

```text
rate:upload-token:user:{uid}
```

例如一分钟最多请求 10 次。

初级版本可以使用：

```text
INCR key
第一次请求时设置 EXPIRE
```

但要认识到：

```text
INCR
EXPIRE
```

是两条命令，中间发生异常可能导致 Key 没有过期时间。

进一步应使用 Lua 脚本，把多个命令作为一个原子操作执行。

## 7.4 这一阶段要学习的知识

- 固定窗口限流；
- TTL；
- Redis 原子自增；
- Lua 脚本的基本作用；
- 按用户限流与按 IP 限流的区别；
- 限流异常如何统一返回。

## 7.5 完成标准

- [ ] 密码错误会增加失败次数；
- [ ] 达到限制后会暂时禁止继续尝试；
- [ ] 登录成功会清除失败次数；
- [ ] Key 有正确的过期时间；
- [ ] 上传凭证接口有合理限流；
- [ ] 有单元测试或集成测试；
- [ ] Redis 异常不会被错误地当成密码错误。

# 八、第 3 阶段：播放量去重

## 8.1 当前问题

如果前端重复上报播放事件，每次都直接增加 MySQL 播放量，可能出现：

- 用户刷新页面导致播放量不断增长；
- 前端重试导致重复计数；
- 恶意脚本刷播放量；
- 热门视频对应的数据库行被高频更新。

## 8.2 第一版设计

已登录用户的 Key：

```text
video:play:dedup:{vid}:{uid}
```

执行：

```text
SET video:play:dedup:100:20 1 NX EX 300
```

结果：

- 设置成功：五分钟内第一次有效播放，可以增加播放量；
- 设置失败：五分钟内已经记录过，不再重复增加。

## 8.3 为什么必须设置过期时间

如果不设置 TTL，该用户对这个视频以后永远不会再增加播放量。

播放量的统计口径需要明确。例如第一版可以规定：

> 同一个登录用户对同一个视频，五分钟内只统计一次有效播放。

这不是唯一正确标准，但必须有明确、可解释的业务规则。

## 8.4 未登录用户怎么办

当前菲比啾比主要通过登录拦截访问接口，可以先只处理登录用户。

以后开放游客播放时，可以考虑：

```text
video:play:dedup:{vid}:{ipHash}:{userAgentHash}
```

但 IP 和 User-Agent 并不能准确代表一个真实用户，因此只能作为弱去重手段。

## 8.5 完成标准

- [ ] 有明确的有效播放定义；
- [ ] 使用 `SET NX EX` 完成短时间去重；
- [ ] 第一次播放增加统计；
- [ ] 有效期内重复播放不增加统计；
- [ ] TTL 到期后可以再次统计；
- [ ] Redis Key 命名统一；
- [ ] 有重复播放测试。

# 九、第 4 阶段：视频互动统计缓存

## 9.1 这是 Redis 部分的核心项目功能

视频统计包括：

- 播放量；
- 点赞量；
- 点踩量；
- 投币量；
- 分享量；
- 收藏量；
- 评论量；
- 弹幕量。

可以使用 Redis Hash：

```text
video:stats:{vid}
```

字段：

```text
play
like
unlike
coin
share
collect
comment
danmu
```

## 9.2 先区分业务事实和聚合统计

以点赞为例：

```text
用户 20 是否点赞视频 100
```

属于用户行为事实，应保存在 `user_video` 表中。

```text
视频 100 一共有多少点赞
```

属于聚合统计，可以缓存到 Redis。

因此不要把点赞接口简单改成：

```text
Redis 点赞数 +1
```

正确思路是：

```text
校验用户原状态
  ↓
使用 MySQL 保存用户行为变化
  ↓
确认状态确实变化
  ↓
修改 Redis 聚合统计
```

## 9.3 第一版推荐采用 Cache Aside

视频详情查询：

```text
先查 Redis 中的视频统计
  ↓
Redis 未命中
  ↓
查询 MySQL 的 video_status
  ↓
将统计写入 Redis，并设置 TTL
```

互动更新：

```text
先完成 MySQL 事务
  ↓
事务提交成功
  ↓
删除对应 Redis 统计缓存
  ↓
下次查询重新加载
```

这一版更容易保证正确性，适合 Redis 初学阶段。

## 9.4 第二版再学习 Redis 计数和批量刷库

熟悉缓存后，可以升级为：

```text
有效互动发生
  ↓
Redis 原子增加或减少统计
  ↓
定时任务批量把增量写回 MySQL
```

这时必须处理：

- Redis 重启导致尚未刷库的数据丢失；
- 定时任务重复执行；
- 刷库期间又产生新增量；
- 多实例重复刷库；
- Redis 统计和 MySQL 统计对账；
- 计数不能出现负数。

因此，不要把“Redis 计数后定时刷库”作为第一个 Redis 功能。

## 9.5 两种方案的学习顺序

### 第一版：缓存查询结果

优点：

- 易理解；
- 对原有写入逻辑改动小；
- MySQL 仍然是准确数据源；
- 容易回退。

### 第二版：Redis 承担高频计数

优点：

- 更能降低热点视频对 MySQL 的写压力；
- 面试展示价值更高。

缺点：

- 最终一致性更复杂；
- 需要刷库和补偿机制。

推荐顺序：

```text
先做 Cache Aside
  ↓
掌握缓存一致性
  ↓
再做 Redis 原子计数和定时刷库
```

## 9.6 完成标准

第一版：

- [ ] 视频统计可以从 Redis 读取；
- [ ] 缓存未命中时会查询 MySQL；
- [ ] 缓存有 TTL；
- [ ] 业务更新后缓存会失效；
- [ ] 不会缓存错误数据；
- [ ] 有缓存命中和未命中测试。

进阶版：

- [ ] Redis 使用原子命令修改统计；
- [ ] 有批量刷库任务；
- [ ] 刷库操作幂等或有明确增量边界；
- [ ] 有失败补偿；
- [ ] 有 Redis 与 MySQL 对账方案；
- [ ] 可以解释数据是强一致还是最终一致。

# 十、第 5 阶段：视频详情缓存

## 10.1 Cache Aside 模式

查询流程：

```text
查询 Redis
  ├── 命中：直接返回
  └── 未命中：查询 MySQL
               ↓
             写入 Redis
               ↓
             返回结果
```

更新流程推荐：

```text
更新 MySQL
  ↓
删除 Redis 缓存
```

不建议初学阶段同时更新数据库和缓存，因为两个系统之间无法通过一个普通本地事务做到真正原子提交。

## 10.2 Key 设计

```text
video:detail:{vid}
```

TTL 不要让大量 Key 在同一秒过期，可以添加随机值：

```text
基础过期时间 + 随机秒数
```

## 10.3 三个常见缓存问题

### 缓存穿透

查询数据库中根本不存在的视频，每次都绕过缓存访问数据库。

初级处理方式：短时间缓存空值。

### 缓存击穿

某个热门视频缓存失效，大量请求同时查询数据库。

可使用互斥锁或逻辑过期处理，但不建议在第一版中过度实现。

### 缓存雪崩

大量 Key 同时过期，数据库压力突然升高。

可以通过随机 TTL 缓解。

## 10.4 完成标准

- [ ] 使用统一的缓存 Key 命名；
- [ ] 视频详情缓存有 TTL；
- [ ] 修改、审核、删除视频时删除缓存；
- [ ] 不存在的视频使用短 TTL 空值缓存；
- [ ] TTL 有适当随机值；
- [ ] 可以解释缓存穿透、击穿和雪崩的区别。

# 十一、第 6 阶段：RabbitMQ 基础与本地环境

## 11.1 学习目标

先不接入投稿业务，完成最小消息示例：

```text
生产者发送一条消息
  ↓
RabbitMQ 保存并路由消息
  ↓
消费者接收并打印消息
```

## 11.2 Spring Boot 依赖

后续开发时需要添加：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-amqp</artifactId>
</dependency>
```

## 11.3 必须理解的概念

### Queue

消息队列，保存等待消费的消息。

### Exchange

交换机，接收生产者消息，并按照规则路由到队列。

### Routing Key

路由键，用来决定消息进入哪个队列。

### Binding

交换机与队列之间的绑定关系。

### Producer

发送消息的服务。

### Consumer

接收并处理消息的服务。

### Ack

消费者告诉 RabbitMQ：消息已经处理成功，可以删除。

## 11.4 第一轮只学习 Direct Exchange

示例：

```text
Exchange：video.events
Routing Key：video.submitted
Queue：video.audit.queue
```

路由过程：

```text
VideoSubmittedEvent
  ↓ routing key = video.submitted
video.events
  ↓
video.audit.queue
  ↓
VideoSubmittedConsumer
```

第一轮不要同时学习所有 Exchange 类型。先掌握 Direct Exchange，再了解 Topic Exchange。

## 11.5 完成标准

- [ ] RabbitMQ 可以通过 Docker Compose 启动；
- [ ] 可以访问 RabbitMQ 管理页面；
- [ ] Spring Boot 可以连接 RabbitMQ；
- [ ] 能声明 Exchange、Queue 和 Binding；
- [ ] 生产者可以发送消息；
- [ ] 消费者可以收到消息；
- [ ] 能在管理页面看到队列和消息状态；
- [ ] 理解 Ack 的基本含义。

# 十二、第 7 阶段：投稿成功后的异步审核任务

## 12.1 为什么作为第一个 MQ 业务

视频投稿完成后天然存在后续任务：

- 创建待审核任务；
- 内容安全检测；
- 视频转码；
- 截图；
- 通知管理员；
- 清理临时文件。

这些任务不需要全部阻塞投稿接口，因此非常适合消息队列。

## 12.2 事件设计

推荐定义：

```java
public record VideoSubmittedEvent(
        String eventId,
        Integer videoId,
        Integer userId,
        String videoObjectKey,
        String coverObjectKey,
        LocalDateTime submittedAt
) {
}
```

注意：事件对象只携带消费者真正需要的数据，不要直接把完整数据库 Entity 当作消息发送。

## 12.3 第一版消费者做什么

第一版不要立即做真正的视频转码。可以先做：

- 接收投稿消息；
- 根据 `videoId` 查询视频；
- 检查视频是否仍处于待审核状态；
- 创建或确认审核任务；
- 记录结构化日志。

这样能先学会完整消息流程，而不是同时陷入音视频处理。

## 12.4 事务提交后再发送

错误流程：

```text
发送消息成功
  ↓
数据库事务回滚
  ↓
消费者收到一个数据库中不存在的视频 ID
```

第一版可以采用：

```text
数据库事务提交成功
  ↓
再发送 VideoSubmittedEvent
```

可以先学习 Spring 的事务事件：

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
```

需要理解：这能避免事务回滚后发送消息，但仍然不能完全解决“数据库已提交，发送 MQ 时应用宕机”的问题。

该问题在后面的本地消息表阶段解决。

## 12.5 完成标准

- [ ] 投稿事务成功后才发送消息；
- [ ] 事务回滚时不发送消息；
- [ ] 消息包含唯一 `eventId`；
- [ ] 消费者能根据 `videoId` 正确查询视频；
- [ ] 消费者会校验当前视频状态；
- [ ] 重复消费不会重复创建审核任务；
- [ ] 有投稿成功和投稿回滚测试。

# 十三、第 8 阶段：审核结果事件

## 13.1 推荐事件

- 创建站内通知；
- 更新热门榜候选；

## 13.3 审核拒绝后的异步任务

可以逐步增加：

- 创建驳回通知；
- 保存驳回原因；

- 检查管理员权限；
- 检查状态流转；
- 修改审核状态；

# 十四、第 9 阶段：消息可靠性

这一阶段非常重要。只会发送和接收消息，还不能算真正掌握 MQ。

## 14.1 生产者确认

生产者需要知道消息是否成功到达 RabbitMQ。

应该学习：

- Publisher Confirm；
- Return Callback；
- 消息发送失败日志；
- 失败后的重试或补偿。

## 14.2 消费者手动确认

正确顺序：

```text
消费者收到消息
  ↓
执行业务
  ↓
业务成功
  ↓
ACK
```

如果业务还没完成就提前确认，消费者随后崩溃，这条消息可能丢失。

## 14.3 消费重试

消费失败不应该无限立即重试，否则可能形成死循环并持续占用资源。

推荐设计：

```text
第一次失败
  ↓
延迟后重试
  ↓
达到最大次数
  ↓
进入死信队列
```

## 14.4 死信队列

多次处理失败的消息进入专门队列，方便：

- 查看失败原因；
- 人工处理；
- 修复问题后重新投递；
- 避免阻塞正常消息。

例如：

```text
video.audit.queue
  ↓ 多次失败
video.audit.dead.queue
```

## 14.5 消费幂等

RabbitMQ 可能重复投递消息。因此消费者必须允许同一个消息执行多次而不产生错误结果。

错误示例：

```text
每收到一次 VideoLikedEvent
就把点赞数 +1
```

如果消息重复，点赞数会多加。

推荐给每条消息添加：

```text
eventId
```

简单版本可使用 Redis：

```text
mq:consumed:{eventId}
```

执行：

```text
SET mq:consumed:{eventId} 1 NX EX 86400
```

但对于重要消费，更可靠的方案是数据库消费记录表，并对 `event_id` 添加唯一索引。

## 14.6 完成标准

- [ ] 生产者启用发送确认；
- [ ] 消费者业务成功后再 ACK；
- [ ] 消费失败可以有限次数重试；
- [ ] 超过重试次数进入死信队列；
- [ ] 消息包含唯一事件 ID；
- [ ] 消费者重复处理同一事件不会重复修改业务数据；
- [ ] 可以通过日志定位消息失败原因。

# 十五、第 10 阶段：本地消息表与最终一致性

## 15.1 为什么需要本地消息表

即使使用事务提交后发送消息，仍可能出现：

```text
MySQL 事务提交成功
  ↓
应用在发送 RabbitMQ 消息前宕机
  ↓
视频已经投稿，但没有投稿事件
```

普通本地事务不能同时保证 MySQL 和 RabbitMQ 一起成功。

## 15.2 Transactional Outbox

在同一个 MySQL 事务中写入：

```text
video
video_status
message_outbox
```

只要事务成功，业务数据和待发送消息记录就一定同时存在。

后台任务扫描：

```text
message_outbox 中未发送的记录
  ↓
发送到 RabbitMQ
  ↓
发送成功后标记为已发送
```

表可以包含：

```text
id
event_id
event_type
aggregate_id
payload
status
retry_count
next_retry_at
created_at
sent_at
```

## 15.3 必须考虑的问题

- 发送成功但更新 outbox 状态失败，可能导致重复发送；
- 因此消费者仍然必须幂等；
- 扫描任务多实例运行时需要避免重复抢占；
- 失败消息需要设置最大重试次数；
- 长期成功记录需要归档或清理。

## 15.4 初学阶段为什么不先做它

本地消息表会同时涉及：

- 数据库事务；
- 定时任务；
- 消息发送；
- 状态机；
- 重试；
- 消费幂等；
- 最终一致性。

如果尚未理解 RabbitMQ 的基本流程，直接做 Outbox 很容易只会复制代码而不理解原因。

## 15.5 完成标准

- [ ] 业务数据和 outbox 记录处于同一事务；
- [ ] 后台任务可以投递未发送消息；
- [ ] 发送失败会记录重试次数；
- [ ] 发送成功会更新状态；
- [ ] 重复发送不会导致重复业务结果；
- [ ] 有长期失败消息的人工处理方式；
- [ ] 可以解释为什么这是最终一致性而不是强一致性。

# 十七、暂时不要做的事情

## 17.1 不要先做 Redis 分布式锁

项目当前大多数并发问题应该优先通过：

- 数据库事务；
- 唯一索引；
- 条件更新；
- 受影响行数；
- 行锁；
- 乐观锁。

解决。

只有多个应用实例确实需要争抢同一份跨进程资源时，再考虑分布式锁。

## 17.2 不要把所有查询都缓存

缓存越多，失效点越多，一致性越复杂。

优先缓存：

- 视频详情；
- 视频统计；
- 热门榜单。

不要一上来缓存所有用户、所有列表和所有分页结果。

## 17.3 不要把用户余额只放在 Redis

用户硬币余额是重要数据，必须以 MySQL 为最终可信来源，并通过事务和条件更新防止超扣。

## 17.4 不要让每个业务都发送 MQ 消息

注册、登录、普通资料修改的核心结果都需要同步完成。

只有欢迎通知、审计日志等附加任务才适合异步，而且当前项目可以后做。

## 17.5 不要立刻做 Kafka、微服务和 Elasticsearch

当前优先级应该是：

```text
单体业务正确
→ 测试完整
→ Redis
→ RabbitMQ
→ 消息可靠性
```

技术数量不是项目质量。能解释技术解决了什么问题，比罗列大量中间件更重要。
