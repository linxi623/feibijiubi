# 菲比啾比视频审核状态设计与实现指南

> 适用项目：菲比啾比后端  
> 技术栈：Java 17、Spring Boot、MyBatis、MySQL  
> 目标：使用枚举、Service 业务校验、原子 SQL 和数据库事务，实现安全、清晰且能够处理并发的视频审核流程。

---

## 一、本章要解决什么问题

菲比啾比的视频投稿完成后，需要经过管理员审核，才能公开展示。

第一版审核流程如下：

```text
用户提交视频
  ↓
PENDING（待审核）
  ├──→ APPROVED（审核通过）
  └──→ REJECTED（审核驳回）
```

第一版只允许以下状态流转：

```text
PENDING → APPROVED
PENDING → REJECTED
```

不允许：

```text
PENDING  → PENDING
APPROVED → APPROVED
APPROVED → REJECTED
REJECTED → REJECTED
REJECTED → APPROVED
```

如果以后需要支持重新投稿、复审或管理员下架，应重新设计对应的状态流转规则，不能随意开放状态之间的相互修改。

本章最终需要解决四个问题：

1. 如何避免在代码中散落 `0`、`1`、`2` 等魔法数字；
2. 如何在 Java 中判断状态流转是否合法；
3. 如何防止两个管理员同时审核导致结果相互覆盖；
4. 如何保证视频状态和审核记录同时成功或同时回滚。

# 二、当前数据库状态定义

当前 `video` 表中的审核状态定义为：

```sql
status TINYINT NOT NULL DEFAULT 0
COMMENT '状态 0审核中 1通过审核 2打回整改 3违规删除'
```

状态含义如下：

| 数据库存值 | Java 枚举 | 含义 |
|---:|---|---|
| 0 | `PENDING` | 待审核 |
| 1 | `APPROVED` | 审核通过 |
| 2 | `REJECTED` | 审核驳回 |
| 3 | `REMOVED` | 违规删除 |

数据库可以继续使用 `TINYINT`，Java 业务代码通过枚举表达状态含义。

虽然第一版审核接口只处理 `PENDING`、`APPROVED` 和 `REJECTED`，但数据库中已经存在状态 `3`，因此 Java 枚举也应该将其定义完整。

# 三、为什么要使用枚举

如果不使用枚举，代码中可能出现：

```java
video.setStatus(0);

if (video.getStatus() == 1) {
    // ...
}
```

阅读代码的人很难直接知道：

- `0` 代表什么；
- `1` 代表什么；
- 哪些状态之间允许转换；
- 数据库中是否还有其他状态。

这种没有明确业务含义的数字通常称为“魔法数字”。

使用枚举后，可以写成：

```java
video.setStatus(VideoReviewStatus.PENDING.getCode());
```

以及：

```java
if (currentStatus == VideoReviewStatus.APPROVED) {
    // ...
}
```

这样可以直接从代码中看出业务含义。

# 四、完整的视频审核状态枚举

建议不要将枚举放在 `entity` 包中，而是创建独立的枚举包：

```text
src/main/java/com/feibijiubi/backend/enums/VideoReviewStatus.java
```

完整代码：

```java
package com.feibijiubi.backend.enums;

import com.feibijiubi.backend.common.BusinessException;

public enum VideoReviewStatus {

    PENDING(0, "待审核"),
    APPROVED(1, "审核通过"),
    REJECTED(2, "审核驳回"),
    REMOVED(3, "违规删除");

    private final int code;
    private final String description;

    VideoReviewStatus(int code, String description) {
        this.code = code;
        this.description = description;
    }

    public int getCode() {
        return code;
    }

    public String getDescription() {
        return description;
    }

    /**
     * 根据数据库中的状态码获取对应枚举。
     */
    public static VideoReviewStatus fromCode(Integer code) {
        if (code == null) {
            throw new BusinessException(500, "视频审核状态不能为空");
        }

        for (VideoReviewStatus status : values()) {
            if (status.code == code) {
                return status;
            }
        }

        throw new BusinessException(500, "未知的视频审核状态：" + code);
    }

    /**
     * 判断当前状态是否允许流转到目标状态。
     */
    public boolean canTransitionTo(VideoReviewStatus targetStatus) {
        if (targetStatus == null) {
            return false;
        }

        return this == PENDING
                && (targetStatus == APPROVED || targetStatus == REJECTED);
    }
}
```

# 五、枚举代码逐段讲解

## 1. 枚举项

```java
PENDING(0, "待审核"),
APPROVED(1, "审核通过"),
REJECTED(2, "审核驳回"),
REMOVED(3, "违规删除");
```

每一个枚举项都包含：

```text
数据库状态码 + 中文说明
```

例如：

```java
PENDING(0, "待审核")
```

表示：

```text
Java 枚举：PENDING
数据库值：0
业务含义：待审核
```

## 2. 成员字段

```java
private final int code;
private final String description;
```

其中：

- `code` 用于和数据库中的 `TINYINT` 状态值对应；
- `description` 用于日志、异常信息或管理端页面展示。

字段声明为 `final`，表示枚举实例创建后，其状态码和描述不能再被修改。

## 3. 构造方法

```java
VideoReviewStatus(int code, String description) {
    this.code = code;
    this.description = description;
}
```

枚举项：

```java
PENDING(0, "待审核")
```

实际上是在调用该构造方法。

枚举构造方法不需要、也不能声明为 `public`。它只用于 Java 在枚举类内部创建固定的枚举实例。

## 4. Getter

```java
public int getCode() {
    return code;
}

public String getDescription() {
    return description;
}
```

使用示例：

```java
int code = VideoReviewStatus.PENDING.getCode();
String description = VideoReviewStatus.PENDING.getDescription();
```

结果：

```text
code = 0
description = 待审核
```

## 5. 根据数据库状态码获得枚举

数据库查询得到的是：

```java
Integer status = video.getStatus();
```

为了在业务代码中使用枚举，可以调用：

```java
VideoReviewStatus currentStatus =
        VideoReviewStatus.fromCode(video.getStatus());
```

`fromCode()` 会遍历所有枚举项：

```java
for (VideoReviewStatus status : values()) {
    if (status.code == code) {
        return status;
    }
}
```

如果数据库状态为空或出现未定义的数字，说明数据异常，因此抛出系统业务异常。

## 6. 判断状态流转是否合法

```java
public boolean canTransitionTo(VideoReviewStatus targetStatus) {
    if (targetStatus == null) {
        return false;
    }

    return this == PENDING
            && (targetStatus == APPROVED || targetStatus == REJECTED);
}
```

这里的 `this` 表示当前枚举状态。

例如：

```java
VideoReviewStatus.PENDING
        .canTransitionTo(VideoReviewStatus.APPROVED);
```

此时：

```text
this = PENDING
targetStatus = APPROVED
```

判断结果为 `true`。

状态流转结果如下：

```java
PENDING.canTransitionTo(APPROVED);   // true
PENDING.canTransitionTo(REJECTED);   // true
PENDING.canTransitionTo(PENDING);    // false

APPROVED.canTransitionTo(APPROVED);  // false
APPROVED.canTransitionTo(REJECTED);  // false

REJECTED.canTransitionTo(APPROVED);  // false
REJECTED.canTransitionTo(REJECTED);  // false
```

# 六、投稿时如何使用枚举

投稿时不要再写：

```java
video.setStatus(0);
```

应该写成：

```java
video.setStatus(VideoReviewStatus.PENDING.getCode());
```

这样可以清楚地表达：

> 新投稿的视频默认进入待审核状态。

如果当前 `VideoServiceImpl` 中存在类似：

```java
private static final int VIDEO_STATUS_REVIEWING = 0;
```

引入枚举后，可以逐步删除该常量，统一使用：

```java
VideoReviewStatus.PENDING.getCode()
```

不要同时维护枚举和重复的状态常量，否则以后修改状态定义时容易出现不一致。

# 七、审核请求 DTO 设计

建议创建：

```text
src/main/java/com/feibijiubi/backend/dto/VideoReviewDTO.java
```

第一版代码：

```java
package com.feibijiubi.backend.dto;

import jakarta.validation.constraints.NotBlank;
import lombok.Data;

@Data
public class VideoReviewDTO {

    /**
     * APPROVED 或 REJECTED。
     */
    @NotBlank(message = "审核结果不能为空")
    private String result;

    /**
     * 驳回视频时必须填写。
     */
    private String reason;
}
```

审核通过请求：

```json
{
  "result": "APPROVED",
  "reason": null
}
```

审核驳回请求：

```json
{
  "result": "REJECTED",
  "reason": "封面与视频内容不符"
}
```

相比：

```json
{
  "approved": true
}
```

使用 `APPROVED` 和 `REJECTED` 可读性更高，而且未来增加其他审核结果时更容易扩展。

`reason` 是否必填取决于 `result`，这是两个字段之间的关联业务规则，因此可以在 Service 中检查：

```java
if (targetStatus == VideoReviewStatus.REJECTED
        && !StringUtils.hasText(request.getReason())) {
    throw new BusinessException(400, "驳回视频时必须填写驳回原因");
}
```

# 八、Mapper 原子状态更新

## 1. 为什么不能先查询再无条件更新

假设管理员 A 和管理员 B 同时审核同一个视频。

两个请求都先查询：

```text
当前状态：PENDING
```

管理员 A 想审核通过，管理员 B 想审核驳回。

如果使用无条件更新：

```sql
UPDATE video
SET status = #{newStatus}
WHERE vid = #{vid};
```

就可能发生：

```text
管理员 A：PENDING → APPROVED
管理员 B：APPROVED → REJECTED
```

管理员 B 的结果覆盖了管理员 A，违反了第一版状态流转规则。

因此，更新 SQL 必须同时检查旧状态。

## 2. VideoMapper 接口

在 `VideoMapper` 中增加：

```java
int updateReviewStatus(
        @Param("vid") Integer vid,
        @Param("oldStatus") Integer oldStatus,
        @Param("newStatus") Integer newStatus
);
```

示例：

```java
package com.feibijiubi.backend.mapper;

import com.feibijiubi.backend.entity.Video;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Param;

@Mapper
public interface VideoMapper {

    Video selectByVid(Integer vid);

    int updateReviewStatus(
            @Param("vid") Integer vid,
            @Param("oldStatus") Integer oldStatus,
            @Param("newStatus") Integer newStatus
    );
}
```

## 3. MyBatis XML

在 `VideoMapper.xml` 中增加：

```xml
<update id="updateReviewStatus">
    UPDATE video
    SET status = #{newStatus}
    WHERE vid = #{vid}
      AND status = #{oldStatus}
      AND deleted_at IS NULL
</update>
```

审核时传入：

```text
oldStatus = 0
newStatus = 1
```

最终相当于执行：

```sql
UPDATE video
SET status = 1
WHERE vid = 100
  AND status = 0
  AND deleted_at IS NULL;
```

## 4. 原子更新如何解决并发问题

如果管理员 A 先执行成功：

```text
status：0 → 1
影响行数：1
```

管理员 B 随后尝试：

```sql
UPDATE video
SET status = 2
WHERE vid = 100
  AND status = 0;
```

此时数据库中的状态已经是 `1`，不再满足 `status = 0`，因此：

```text
影响行数：0
```

Service 可以根据影响行数判断审核冲突：

```java
if (rows != 1) {
    throw new BusinessException(
            409,
            "视频已被其他管理员审核，请刷新后重试"
    );
}
```

这就是 SQL 原子条件更新。

# 十、审核 Service 实现

建议创建：

```text
src/main/java/com/feibijiubi/backend/service/impl/video/VideoReviewServiceImpl.java
```

第一版代码：

```java
package com.feibijiubi.backend.service.impl.video;

import com.feibijiubi.backend.common.BusinessException;
import com.feibijiubi.backend.dto.VideoReviewDTO;
import com.feibijiubi.backend.entity.Video;
import com.feibijiubi.backend.enums.VideoReviewStatus;
import com.feibijiubi.backend.mapper.VideoMapper;
import com.feibijiubi.backend.service.video.VideoReviewService;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.util.StringUtils;

import java.util.Locale;

@Service
public class VideoReviewServiceImpl implements VideoReviewService {

    private final VideoMapper videoMapper;

    public VideoReviewServiceImpl(VideoMapper videoMapper) {
        this.videoMapper = videoMapper;
    }

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void reviewVideo(
            Integer reviewerUid,
            Integer vid,
            VideoReviewDTO request
    ) {
        if (reviewerUid == null) {
            throw new BusinessException(401, "请先登录");
        }

        if (vid == null || vid <= 0) {
            throw new BusinessException(400, "视频参数不合法");
        }

        if (request == null || !StringUtils.hasText(request.getResult())) {
            throw new BusinessException(400, "审核结果不能为空");
        }

        VideoReviewStatus targetStatus =
                parseTargetStatus(request.getResult());

        if (targetStatus == VideoReviewStatus.REJECTED
                && !StringUtils.hasText(request.getReason())) {
            throw new BusinessException(400, "驳回视频时必须填写驳回原因");
        }

        Video video = videoMapper.selectByVid(vid);
        if (video == null || video.getDeletedAt() != null) {
            throw new BusinessException(404, "视频不存在");
        }

        VideoReviewStatus currentStatus =
                VideoReviewStatus.fromCode(video.getStatus());

        if (!currentStatus.canTransitionTo(targetStatus)) {
            throw new BusinessException(
                    409,
                    "视频当前状态为“"
                            + currentStatus.getDescription()
                            + "”，不能变更为“"
                            + targetStatus.getDescription()
                            + "”"
            );
        }

        int rows = videoMapper.updateReviewStatus(
                vid,
                VideoReviewStatus.PENDING.getCode(),
                targetStatus.getCode()
        );

        if (rows != 1) {
            throw new BusinessException(
                    409,
                    "视频已被其他管理员审核，请刷新后重试"
            );
        }

        // 后续在这里插入审核记录。
    }

    private VideoReviewStatus parseTargetStatus(String result) {
        try {
            VideoReviewStatus targetStatus = VideoReviewStatus.valueOf(
                    result.trim().toUpperCase(Locale.ROOT)
            );

            if (targetStatus != VideoReviewStatus.APPROVED
                    && targetStatus != VideoReviewStatus.REJECTED) {
                throw new BusinessException(
                        400,
                        "审核结果只能是 APPROVED 或 REJECTED"
                );
            }

            return targetStatus;
        } catch (IllegalArgumentException exception) {
            throw new BusinessException(
                    400,
                    "审核结果只能是 APPROVED 或 REJECTED"
            );
        }
    }
}
```

# 十一、为什么既要 Java 检查，又要 SQL 检查

Service 中进行了两层检查。

## 第一层：Java 状态流转检查

```java
if (!currentStatus.canTransitionTo(targetStatus)) {
    throw new BusinessException(...);
}
```

作用：

- 明确表达业务规则；
- 提前阻止非法状态流转；
- 返回容易理解的错误信息；
- 便于编写状态流转单元测试。

## 第二层：SQL 旧状态条件检查

```sql
AND status = #{oldStatus}
```

作用：

- 防止两个管理员并发审核；
- 防止查询后、更新前数据库状态被其他请求修改；
- 保证只有一个审核请求能够成功；
- 让数据库成为最终一致性保护层。

只写 Java 检查不能解决并发问题，因为查询和更新之间存在时间窗口。

只写 SQL 检查虽然可以保证数据安全，但业务错误信息不够清晰，而且无法在 Java 层明确表达状态流转规则。

因此，两层检查都应该保留。

# 十二、管理员审核 Controller

建议创建管理员专用 Controller：

```text
src/main/java/com/feibijiubi/backend/controller/VideoReviewController.java
```

```java
package com.feibijiubi.backend.controller;

import com.feibijiubi.backend.common.ApiResponse;
import com.feibijiubi.backend.dto.VideoReviewDTO;
import com.feibijiubi.backend.service.video.VideoReviewService;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.validation.Valid;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PutMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/admin/videos")
public class VideoReviewController {

    private final VideoReviewService videoReviewService;

    public VideoReviewController(VideoReviewService videoReviewService) {
        this.videoReviewService = videoReviewService;
    }

    @PutMapping("/{vid}/review")
    public ApiResponse<Void> reviewVideo(
            HttpServletRequest httpRequest,
            @PathVariable Integer vid,
            @Valid @RequestBody VideoReviewDTO request
    ) {
        Integer currentUserId =
                (Integer) httpRequest.getAttribute("currentUserId");

        videoReviewService.reviewVideo(
                currentUserId,
                vid,
                request
        );

        return ApiResponse.success("审核完成", null);
    }
}
```

建议接口：

```http
PUT /api/admin/videos/{vid}/review
```

需要注意：

> URL 中存在 `/admin` 并不代表调用者就是管理员。

Controller 仍然必须配合管理员权限拦截器或权限注解。不能只检查用户是否登录，还必须验证用户角色。

# 十三、管理员权限要求

审核接口至少需要两层身份检查：

```text
第一层：用户是否登录
第二层：登录用户是否为管理员
```

可以设计自定义注解：

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface AdminOnly {
}
```

Controller 使用：

```java
@AdminOnly
@PutMapping("/{vid}/review")
public ApiResponse<Void> reviewVideo(...) {
    // ...
}
```

管理员拦截器负责：

1. 获取当前用户信息；
2. 检查用户角色；
3. 普通用户返回 403；
4. 管理员继续访问。

权限验证不能信任前端提交的角色参数，例如下面这种设计是不安全的：

```json
{
  "uid": 10,
  "role": "ADMIN"
}
```

管理员身份应该来自经过验证的登录凭证，并在必要时结合数据库中的真实角色和账号状态进行检查。

# 十四、审核记录表设计

只修改 `video.status`，只能知道视频的最终状态，无法回答：

- 谁审核了视频；
- 什么时间审核；
- 为什么被驳回；
- 审核前是什么状态；
- 是否发生过重复审核。

因此建议增加审核记录表：

```sql
CREATE TABLE video_review_record (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    vid INT NOT NULL,
    reviewer_uid INT NOT NULL,
    old_status TINYINT NOT NULL,
    new_status TINYINT NOT NULL,
    reason VARCHAR(500),
    reviewed_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_vid (vid),
    INDEX idx_reviewer_uid (reviewer_uid)
);
```

字段说明：

| 字段 | 含义 |
|---|---|
| `id` | 审核记录主键 |
| `vid` | 被审核的视频 ID |
| `reviewer_uid` | 审核管理员 ID |
| `old_status` | 审核前状态 |
| `new_status` | 审核后状态 |
| `reason` | 驳回原因 |
| `reviewed_at` | 审核时间 |

# 十五、审核记录实体和 Mapper

## 1. 实体

```java
package com.feibijiubi.backend.entity;

import lombok.Data;

import java.time.LocalDateTime;

@Data
public class VideoReviewRecord {

    private Long id;
    private Integer vid;
    private Integer reviewerUid;
    private Integer oldStatus;
```

# 十六、审核事务设计

审核 Service 应添加：

```java
@Transactional(rollbackFor = Exception.class)
```

完整事务流程：

```text
检查登录和管理员权限
  ↓
检查请求参数
  ↓
查询视频
  ↓
检查 Java 状态流转规则
  ↓
使用原子 SQL 更新视频状态
  ↓
插入审核记录
  ↓
全部成功：提交事务
任意一步失败：全部回滚
```

如果状态更新成功，但审核记录插入失败，事务应该回滚状态更新。

这样可以保证：

```text
video.status
```

和：

```text
video_review_record
```

始终保持一致。

需要注意：Spring 数据库事务只能回滚数据库操作，不能自动回滚 COS、HTTP 请求或其他外部系统操作。

当前审核流程如果只修改 MySQL 数据，可以直接使用本地数据库事务。

# 二十一、常见错误

## 错误一：枚举只有字段，没有构造方法

错误示例：

```java
public enum VideoReviewStatus {
    PENDING(0, "待审核"),
    APPROVED(1, "审核通过"),
    REJECTED(2, "审核驳回");

    private final int code;
    private final String description;
}
```

枚举项传入了两个参数，但类中没有对应构造方法，代码无法正常编译。

必须添加：

```java
VideoReviewStatus(int code, String description) {
    this.code = code;
    this.description = description;
}
```

## 错误二：枚举和数据库状态不完整

数据库中定义了状态 `3`，Java 枚举却只定义 `0`、`1`、`2`，会导致数据库和 Java 状态模型不一致。

## 错误三：只在 Java 中判断旧状态

```java
if (video.getStatus() != 0) {
    throw new BusinessException(409, "视频已经审核");
}

videoMapper.updateStatus(vid, newStatus);
```

这种写法不能防止两个管理员并发审核，因为查询和更新是两条独立 SQL。

## 错误四：更新 SQL 没有旧状态条件

```sql
UPDATE video
SET status = #{newStatus}
WHERE vid = #{vid};
```

这会允许后一个请求覆盖前一个审核结果。

## 错误五：不检查 SQL 影响行数

即使 SQL 使用了旧状态条件，也必须检查：

```java
if (rows != 1) {
    throw new BusinessException(409, "视频已被其他管理员审核");
}
```

否则业务层不知道更新是否真正成功。

## 错误六：状态更新和审核记录没有事务

如果先更新视频状态，再插入审核记录，而两步不在同一事务中，可能出现：

```text
视频已经审核通过
但审核记录保存失败
```

因此两步必须放在同一个事务中。

## 错误七：只看 `/admin` 路径，不验证管理员角色

URL 名称不能提供安全保护，必须在服务端验证当前用户的真实角色。

## 错误八：待审核视频也能公开互动

如果播放、点赞等逻辑只判断视频是否存在，而不判断审核状态，待审核或被驳回的视频仍然可能产生公开互动数据。

# 二十二、核心设计总结

视频审核状态设计可以概括为四层保护：

```text
枚举
负责定义状态含义和允许的状态流转

Service
负责参数、权限和业务规则校验

原子 UPDATE
负责保证并发情况下只有一个审核请求成功

数据库事务
负责保证视频状态与审核记录同时成功或同时失败
```

完整审核流程：

```text
管理员提交审核请求
  ↓
验证登录状态和管理员角色
  ↓
解析目标审核状态
  ↓
查询视频当前状态
  ↓
枚举判断状态流转是否合法
  ↓
原子 SQL：仅当旧状态仍为 PENDING 时更新
  ↓
检查 SQL 影响行数
  ↓
保存审核记录
  ↓
提交事务
```

最关键的原则是：

> 枚举表达规则，Service 执行业务，原子 SQL 防止并发覆盖，事务保证多表一致性。
